# Что нужно

- Python 3.11+
- Postgres 16
- `ffmpeg` и `ffprobe` в `PATH` — ими делаются превью
- Объектное хранилище: локально MinIO из `../api/docker-compose.yml`, в проде Google Cloud Storage
  («Хранилище Google» ниже)

# Postgres и хранилище

Канонная локальная база и бакет — те же, что у API, одной командой:

```sh
cd ../api && docker compose up -d
```

Если её ещё нет (или нужна отдельная), сгодится любой Postgres 16:

```sh
docker run --rm -d --name remember-pg \
  -e POSTGRES_USER=remember -e POSTGRES_PASSWORD=remember -e POSTGRES_DB=remember \
  -p 5432:5432 postgres:16
```

# Запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env             # база и локальное хранилище
set -a && . ./.env && set +a     # внести в окружение: воркер читает только его

python -m montage init           # создать таблицы воркера
python -m montage tracks         # выложить музыку в хранилище (jobs/montage.md, «Треки»)
python -m montage run            # цикл разбора очереди, Ctrl-C для остановки
```

Своего чтения `.env` у воркера нет — переменные приходят из окружения, и на хостинге их задаёт
сам сервис. Имена хранилища — те же четыре, что читает API, так что вместо своего `.env` можно
внести его `../api/.env` целиком.

`init` можно звать сколько угодно раз: `schema.sql` идемпотентен (`CREATE TABLE IF NOT EXISTS`),
на чистой базе накатывается с нуля.

Необязательный `R2_REGION` (по умолчанию `auto`) — на случай хранилища, которому не всё равно,
чем подписан запрос.

`API_URL` и `INTERNAL_WORKER_TOKEN` нужны только готовому ролику — ими воркер стучится в API,
чтобы тот разослал пуш. Не заданы — сборка всё равно проходит, в логе остаётся предупреждение.

# Хранилище Google

В проде бакет — Google Cloud Storage, и воркер говорит с ним тем же S3-протоколом, что с MinIO:
через XML API Google. Переменные те же `R2_*` — имена остались от Cloudflare R2, их же читают API
и стенд:

```sh
R2_ENDPOINT=https://storage.googleapis.com
R2_BUCKET=<имя бакета>
R2_ACCESS_KEY_ID=<access id HMAC-ключа, начинается с GOOG>
R2_SECRET_ACCESS_KEY=<секрет HMAC-ключа>
# R2_REGION не задаётся: по умолчанию `auto`, его Google и советует S3-клиентам
```

Ключ — HMAC-ключ (пара «ключ/секрет») сервисного аккаунта, а не его JSON-ключ: воркер говорит
по S3. Права на бакет, которые нужны воркеру: `storage.objects.get` (скачать, проверить наличие),
`storage.objects.create` и `storage.objects.delete` (положить, перезаписать, удалить),
`storage.multipartUploads.create` (крупный файл уходит кусками) и `storage.multipartUploads.abort`
(уборка оборванных загрузок).

Чем Google отличается от S3 и MinIO и что с этим сделано (`montage/storage.py`):

- **Контрольные суммы.** boto3 начиная с 1.36 сам добавляет к каждой загрузке заголовки
  `x-amz-checksum-*`, а по HTTPS шлёт тело `aws-chunked` с суммой в трейлере, и к каждому
  скачиванию просит сумму назад. Google этих заголовков не знает. Клиент настроен слать их только
  там, где без них нельзя, — ни одному запросу воркера они не нужны. Держит это настройка клиента,
  а не пин версии: обновление boto3 её не отменит.
- **«Уже нет».** На удаление ключа, под которым пусто, Google отвечает 404 `NoSuchKey`, S3 и
  MinIO — 204. Загрузку, которая уже оборвана или завершена, S3 и MinIO на обрыв называют 404
  `NoSuchUpload`; Google так отвечает на части и завершение по такому id, а про обрыв его
  документация молчит — это живой контроль и смотрит. Для воркера всё это итог, а не сбой: 404 с
  любым кодом, кроме «нет такого бакета», значит «уже нет» (`storage.missing`).
- **Незавершённые загрузки** Google сам не удаляет никогда. Их обрывает ежечасная уборка
  (`queue.md`); правило жизненного цикла у бакета, обрывающее загрузки старше нескольких дней, —
  страховка на случай, когда воркер не работает, и ставится у бакета, а не здесь.

## Живой контроль

Один: `tests/test_storage.py`, направленный на бакет Google для проверок — не на рабочий. Файл в
9 МиБ уходит кусками, наличие и тип читаются с бакета, файл скачивается диапазонами и сверяется
побайтно, удаляется — дважды, второй раз по пустому ключу; незавершённая загрузка обрывается,
обрывается повторно, а завершённая без ведома API — удаляется. В каждом отправленном запросе
проверяется, что контрольных сумм S3 в нём нет. Пишет только под своим префиксом
`storage-check/<uuid>/` и вычищает его за собой, даже упав.

Ключи и имя бакета — только из окружения, внесённые из того места, где их держат (не из
репозитория и не с `.env` рабочего бакета):

```sh
# в окружении: R2_ENDPOINT=https://storage.googleapis.com, R2_BUCKET=<бакет для проверок>,
# R2_ACCESS_KEY_ID и R2_SECRET_ACCESS_KEY — ключ бакета для проверок
python -m pytest tests/test_storage.py
```

Базы ему не нужно. Ключу бакета для проверок, кроме прав воркера, нужны `storage.objects.list` и
`storage.multipartUploads.list`: ими контроль находит, что убрать, и видит, что оборванной загрузки
больше нет. Направлять на Google только этот файл: остальной набор пишет в бакет и за собой не
убирает. В обычном прогоне набора тот же файл идёт в MinIO.

# Фиктивная задача

В другом терминале (с тем же окружением):

```sh
python -m montage enqueue dummy        # воркер её возьмёт и поставит done
python -m montage enqueue dummy fail   # ref=fail — упадёт и уйдёт в повтор
```

Второй вариант и есть проверка повторов: воркер отметит попытку, запишет ошибку и отложит задачу
(30 с, потом 60 с), а после третьей попытки поставит `failed`.

# Образ

`Dockerfile` — две стадии на одной основе: последняя — боевой образ, `test` — среда
`test-in-docker.sh`. CI (`.gitlab-ci.yml`) на каждый пуш в main собирает боевой и кладёт в реестр
проекта `git.dapp-devs.com:5050/nox-labs/nox/remember/montage` с тегом по SHA коммита. Выкатки в
CI нет.

| Команда | Когда | Из окружения |
|---|---|---|
| `python -m montage run` (по умолчанию) | основной процесс пода | всё ниже |
| `python -m montage init` | на каждый выклад, до `run` (идемпотентна) | `DATABASE_URL` |
| `python -m montage tracks` | на каждый выклад (идемпотентна) | четыре `R2_*` |
| `python -m montage enqueue dummy` | руками: жив ли воркер | `DATABASE_URL` |

Окружение — только переменные, значения задаёт тот, кто выкатывает:

- `DATABASE_URL` — обязательна;
- `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` — обязательны, `R2_REGION`
  — нет («Хранилище Google»);
- `AI_PROVIDER=gemini` и `GEMINI_API_KEY`, необязательная `GEMINI_MODEL` — без них облачная модель
  пропускается, о чём сказано в логе;
- `API_URL` и `INTERNAL_WORKER_TOKEN` — пуш о готовом ролике.

Секреты из них — `DATABASE_URL`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `GEMINI_API_KEY`,
`INTERNAL_WORKER_TOKEN`.

Под:

- портов и HTTP-проб нет: жив ли воркер, видно по логу и очереди; одна реплика;
- пользователь `10001`, не root; корень можно держать только на чтение, если `/tmp` — том на
  запись: там рабочие папки задач и кэш numba (`NUMBA_CACHE_DIR`). Том на диске, не в памяти;
- остановка — SIGINT (`STOPSIGNAL` образа), воркер выходит сразу. Задача, прерванная на середине,
  так и остаётся `running` (`worker.py`, `run_once`);
- ffmpeg берёт столько потоков, сколько процессоров видит на узле, а не сколько дано лимитом, и
  память у него растёт вместе с ними.

Образ — 1,16 ГБ распакованный, ~440 МБ сжатый (amd64). Сколько берёт работающий (измерено
25.09.2026 в Docker, 4 процессора, если не сказано иное):

| | Память | `/tmp` |
|---|---|---|
| покой после старта | ~45 МиБ | — |
| покой после первого ролика (librosa остаётся в процессе) | ~250 МиБ | — |
| превью пяти маленьких файлов (10 процессоров) | пик ~310 МиБ | < 1 МиБ |
| ролик из 5 кусков, 11 с | пик 1,1 ГиБ (10 процессоров — 1,45 ГиБ) | ~6 МиБ |
| одна склейка ffmpeg: 5 / 15 / 30 кусков | 0,95 / 2,0 / 3,1 ГиБ | — |

Склейка открывает все куски ролика разом, и каждый добавляет ~80–100 МиБ: память ролика растёт с
его длиной, минутный ролик (кусок по 2,5 с) — порядка 3 ГиБ. Диск задачи ролика — оценка: все оригиналы
воспоминания (api ограничивает их 10 ГиБ) плюс куски и готовый ролик; задачи превью — один
оригинал (до 1 ГиБ) и его копии.
