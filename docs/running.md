# Что нужно

- Python 3.11+
- Postgres 16
- `ffmpeg` и `ffprobe` в `PATH` — ими делаются превью
- Объектное хранилище: локально MinIO из `../api/docker-compose.yml`, в проде Google Cloud Storage
  («Хранилище Google» ниже)

# Postgres и хранилище

Канонная локальная база и бакет — те же, что у API, одной командой:

```sh
cd ../api && docker compose up -d
```

Если её ещё нет (или нужна отдельная), сгодится любой Postgres 16:

```sh
docker run --rm -d --name remember-pg \
  -e POSTGRES_USER=remember -e POSTGRES_PASSWORD=remember -e POSTGRES_DB=remember \
  -p 5432:5432 postgres:16
```

# Запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env             # база и локальное хранилище
set -a && . ./.env && set +a     # внести в окружение: воркер читает только его

python -m montage init           # создать таблицы воркера
python -m montage tracks         # выложить музыку в хранилище (jobs/montage.md, «Треки»)
python -m montage run            # цикл разбора очереди, Ctrl-C для остановки
```

Своего чтения `.env` у воркера нет — переменные приходят из окружения, и на хостинге их задаёт
сам сервис. Имена хранилища — те же четыре, что читает API, так что вместо своего `.env` можно
внести его `../api/.env` целиком.

`init` можно звать сколько угодно раз: `schema.sql` идемпотентен (`CREATE TABLE IF NOT EXISTS`),
на чистой базе накатывается с нуля, а старой добавляет недостающие столбцы (`ADD COLUMN IF NOT
EXISTS`), не трогая строк.

Необязательный `R2_REGION` (по умолчанию `auto`) — на случай хранилища, которому не всё равно,
чем подписан запрос.

`API_URL` и `INTERNAL_WORKER_TOKEN` нужны только готовому ролику — ими воркер стучится в API,
чтобы тот разослал пуш. Не заданы — сборка всё равно проходит, в логе остаётся предупреждение.

# Хранилище Google

С бакетом воркер говорит через одну дверь — `montage/storage.py`: скачать, положить, проверить
наличие, удалить, оборвать незавершённую загрузку. За дверью один из двух драйверов, его выбирает
`STORAGE_DRIVER`: `s3` (по умолчанию — MinIO и всё S3-совместимое по `R2_*`) или `google`.

## Драйвер google — по JSON-ключу служебной учётки

Так воркер работает с Google Cloud Storage на dev-контуре (decision-16): HMAC-ключей к бакету нет,
есть JSON-ключ служебной учётки. Бакет — временно общий бакет компании, и он публичный.

```sh
STORAGE_DRIVER=google
GOOGLE_STORAGE_CREDENTIALS=<содержимое JSON-файла ключа одной строкой — секрет>
GOOGLE_STORAGE_BUCKET=<имя бакета>
GOOGLE_STORAGE_PREFIX=<наша папка в бакете; для работы — remember/dev-media>
```

- **Префикс обязателен.** Бакет общий, рядом лежит чужое. Объект воркера — всегда
  `<бакет>/<префикс>/<ключ>`, где ключ — логический, как в таблицах api (`originals/<uuid>`,
  `previews/<id>.jpg`, …): в базе префикса нет, добавляет его драйвер в одном месте. Тот же
  префикс должен стоять у api — он строит ссылки на те же объекты. Без префикса драйвер не
  создаётся, и воркер не стартует. Ключ, который вывел бы за префикс, — пустой, с `..` или `.`, с
  ведущим `/` или пустым сегментом, с непечатаемым символом, с префиксом внутри (`remember/…`), —
  отказывается громко и до запроса к Google; в ежечасной уборке это предупреждение в логе, а не
  запрос.
- **Бакет публичный** (decision-16, временно): объект прочтёт любой, кто знает его адрес.
  Единственная защита кадра — неугадываемое имя. Имена строит api из uuid, и порядковых имён
  (`1.jpg`, `2.jpg`) быть не должно — ни у api, ни у воркера.
- **Права учётки на бакет** — роль Storage Object User (`roles/storage.objectUser`) или то, что
  воркеру из неё нужно: `storage.objects.get` (скачать, проверить наличие),
  `storage.objects.create` и `storage.objects.delete` (положить, перезаписать, удалить) и
  `storage.multipartUploads.abort` (уборка оборванных загрузок; начинает их api).
- **Как ходит.** XML API: `https://storage.googleapis.com/<бакет>/<префикс>/<ключ>` с
  `Authorization: Bearer`. Токен с областью `devstorage.read_write` получает и обновляет google-auth.
  Файл уходит одним PUT любого размера (XML API берёт объект целиком, кусков нет) и читается с
  диска потоком; скачивается потоком в файл. Таймауты — 10 с на соединение и 60 с на каждое чтение
  или запись; 5xx, 429 и оборванная связь — до четырёх попыток, через 1, 2 и 4 с; 401 — токен
  обновляется один раз. «Уже нет» (404 с любым кодом, кроме «нет такого бакета») — итог, а не
  сбой, как у s3 (`storage.missing`).
- **Ключ** разбирается, когда драйвер создаётся, — на старте воркера (в логе строка `storage:` с
  бакетом и префиксом): битый или не тот JSON останавливает воркер сразу, а не на первой загрузке.
  Ни ключ, ни токен не попадают ни в лог, ни в текст ошибки.

## Драйвер s3 по HMAC-ключу

Тот же Google можно открыть и драйвером s3 — по S3-совместимому XML API, если у бакета есть
HMAC-ключ. Префикса у драйвера s3 нет: в общий бакет его не направлять.

```sh
R2_ENDPOINT=https://storage.googleapis.com
R2_BUCKET=<имя бакета>
R2_ACCESS_KEY_ID=<access id HMAC-ключа, начинается с GOOG>
R2_SECRET_ACCESS_KEY=<секрет HMAC-ключа>
# R2_REGION не задаётся: по умолчанию `auto`, его Google и советует S3-клиентам
```

Прав нужно те же, что драйверу google, и `storage.multipartUploads.create`: крупный файл boto3
шлёт кусками. Чем Google по S3 отличается от S3 и MinIO и что с этим сделано:

- **Контрольные суммы.** boto3 начиная с 1.36 сам добавляет к каждой загрузке заголовки
  `x-amz-checksum-*`, а по HTTPS шлёт тело `aws-chunked` с суммой в трейлере, и к каждому
  скачиванию просит сумму назад. Google этих заголовков не знает. Клиент настроен слать их только
  там, где без них нельзя, — ни одному запросу воркера они не нужны. Держит это настройка клиента,
  а не пин версии: обновление boto3 её не отменит.
- **«Уже нет».** На удаление ключа, под которым пусто, Google отвечает 404 `NoSuchKey`, S3 и
  MinIO — 204. Загрузку, которая уже оборвана или завершена, S3 и MinIO на обрыв называют 404
  `NoSuchUpload`; Google на повторный обрыв отвечает 204, а 404 `NoSuchUpload` — на часть по такому
  id. Для воркера всё это итог, а не сбой: 404 с любым кодом, кроме «нет такого бакета», значит
  «уже нет» (`storage.missing`).

Незавершённые загрузки Google сам не удаляет никогда, каким бы драйвером ни ходить. Их обрывает
ежечасная уборка (`queue.md`); правило жизненного цикла у бакета, обрывающее загрузки старше
нескольких дней, — страховка на случай, когда воркер не работает, и ставится у бакета, а не здесь.

## Живой контроль

**Драйвер google** — последний тест `tests/test_storage_google.py`. Ходит в настоящий бакет, но
только под `remember/dev-check/<uuid>/`: этот префикс он ставит себе сам, что бы ни стояло в
`GOOGLE_STORAGE_PREFIX`, и вычищает за собой всё, что создал, даже упав. Файл в 9 МиБ уходит одним
PUT, размер и тип читаются с бакета, файл скачивается и сверяется побайтно, удаляется — дважды,
второй раз по пустому ключу; незавершённая загрузка обрывается, обрывается повторно, и часть после
обрыва получает `NoSuchUpload`; завершённая без ведома api — удаляется. Каждый отправленный запрос
сверяется: он под префиксом проверок.

```sh
# в окружении: STORAGE_DRIVER=google, GOOGLE_STORAGE_BUCKET=<бакет>,
# GOOGLE_STORAGE_CREDENTIALS=<JSON ключа одной строкой> — из того места, где ключ держат
python -m pytest tests/test_storage_google.py
```

Базы ему не нужно, остальные тесты файла идут без сети; без `STORAGE_DRIVER=google` живой тест
пропускается. Загрузки, которые обрывает, контроль начинает сам — учётке нужно ещё
`storage.multipartUploads.create` (оно в Storage Object User).

**Драйвер s3 с HMAC-ключом** — `tests/test_storage.py`, направленный на бакет Google для проверок,
не на рабочий и не на общий. Файл в 9 МиБ уходит кусками, наличие и тип читаются с бакета, файл
скачивается диапазонами и сверяется побайтно, удаляется — дважды, второй раз по пустому ключу;
незавершённая загрузка обрывается, обрывается повторно, а завершённая без ведома API — удаляется.
В каждом отправленном запросе проверяется, что контрольных сумм S3 в нём нет. Пишет только под
своим префиксом `storage-check/<uuid>/` и вычищает его за собой, даже упав.

```sh
# в окружении: R2_ENDPOINT=https://storage.googleapis.com, R2_BUCKET=<бакет для проверок>,
# R2_ACCESS_KEY_ID и R2_SECRET_ACCESS_KEY — ключ бакета для проверок
python -m pytest tests/test_storage.py
```

Ключу бакета для проверок, кроме прав воркера, нужны `storage.objects.list` и
`storage.multipartUploads.list`: ими контроль находит, что убрать, и видит, что оборванной загрузки
больше нет. Направлять на Google только эти файлы: остальной набор пишет в бакет и за собой не
убирает. В обычном прогоне набора оба идут без Google: первый — на подменённых ответах, второй — в
MinIO.

# Фиктивная задача

В другом терминале (с тем же окружением):

```sh
python -m montage enqueue dummy        # воркер её возьмёт и поставит done
python -m montage enqueue dummy fail   # ref=fail — упадёт и уйдёт в повтор
```

Второй вариант и есть проверка повторов: воркер отметит попытку, запишет ошибку и отложит задачу
(30 с, потом 60 с), а после третьей попытки поставит `failed`.

# Образ

`Dockerfile` — две стадии на одной основе: последняя — боевой образ, `test` — среда
`test-in-docker.sh`. CI (`.gitlab-ci.yml`) на каждый пуш в `dev` собирает боевой, кладёт в реестр
проекта `git.dapp-devs.com:5050/nox-labs/nox/remember/montage` с тегом по SHA коммита и выкатывает
на dev-контур. `main` к CI не привязана — она под боевой контур.

Выкатка — джоба `dev_deploy`, после сборки:

- клонирует репозиторий инфраструктуры `nox-labs/infra/stage/nox-infra-dev`, пишет в
  `ioc-helm/nox/remember/montage/values-dev.yaml` только `image.repository` и `image.tag`, коммитит
  «deploy remember-montage dev <короткий SHA>» и пушит в его `main`; если там успели закоммитить —
  `pull --rebase` и снова, до пяти раз. Дальше приложение `dev-remember-montage` синкает ArgoCD, и
  под обработчика перезапускается — на любой пуш в `dev`, даже если менялись только документы.
  Ключ для пуша — переменная CI `SSH_PRIVATE_KEY`, заведённая на весь GitLab;
- перед коммитом сверяет, что изменён ровно этот файл, в нём — только строки образа, а значения
  остальных полей те же. Иначе падает, ничего не запушив. Тег уже стоит — выходит без коммита.

Прошла ли выкатка: публичного адреса у обработчика нет — смотреть поды в Prometheus
https://prometheus.noxlabs.xyz запросами из README чартов (`ioc-helm/nox/remember/README.md`, «Как
наблюдать выкатку без доступа к кластеру»). Для обработчика главные:

| Что | Запрос |
|---|---|
| Готов ли (1 — да) | `kube_pod_status_ready{exported_namespace="default", exported_pod=~"dev-remember-montage.*", condition="true"}` |
| Почему не стартует создание таблиц | `kube_pod_init_container_status_waiting_reason{exported_namespace="default", exported_pod=~"dev-remember-montage.*"} == 1` |
| Упала выкладка музыки | `kube_job_status_failed{exported_namespace="default", job_name=~"dev-remember-montage.*"} > 0` |

Откат — вернуть прежний тег в `image.tag` того же `values-dev.yaml` и закоммитить в `main`
репозитория инфраструктуры, ArgoCD откатит сам. Прежние теги — в истории файла, в коммитах «deploy
remember-montage dev …». Следующий пуш в `dev` снова выкатит свежий.

Пока чарты Remember не слиты в `main` репозитория инфраструктуры, `dev_deploy` падает: файла там
ещё нет. Это ожидаемо, образ при этом собран; после слияния — перезапустить джобу.

api выкатывается своим пайплайном тем же путём, и какой из двух окажется на dev первым, не угадать.
Контракт между ними — «Пожелания к трекам» (`jobs/montage.md`): пока одна сторона уже новая, а
другая ещё старая, они рассогласованы. Окно короткое, для пилота допустимо.

| Команда | Когда | Из окружения |
|---|---|---|
| `python -m montage run` (по умолчанию) | основной процесс пода | всё ниже |
| `python -m montage init` | на каждый выклад, до `run` (идемпотентна) | `DATABASE_URL` |
| `python -m montage tracks` | на каждый выклад (идемпотентна) | хранилище |
| `python -m montage enqueue dummy` | руками: жив ли воркер | `DATABASE_URL` |

Окружение — только переменные, значения задаёт тот, кто выкатывает:

- `DATABASE_URL` — обязательна;
- хранилище, обязательно одно из двух («Хранилище Google»): `R2_ENDPOINT`, `R2_BUCKET`,
  `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (драйвер s3, по умолчанию; `R2_REGION` — нет) или
  `STORAGE_DRIVER=google` и `GOOGLE_STORAGE_CREDENTIALS`, `GOOGLE_STORAGE_BUCKET`,
  `GOOGLE_STORAGE_PREFIX`. Без них воркер не стартует;
- `AI_PROVIDER=gemini` и `GEMINI_API_KEY`, необязательная `GEMINI_MODEL` — без них облачная модель
  пропускается, о чём сказано в логе;
- `API_URL` и `INTERNAL_WORKER_TOKEN` — пуш о готовом ролике;
- `FFMPEG_THREADS` — необязательна, по умолчанию `2`: сколько потоков у каждого декодера, графа
  фильтров и кодировщика любого ffmpeg воркера. Больше — быстрее и дороже по памяти (цифры ниже);
  не целое число от 1 — воркер не стартует.

Секреты из них — `DATABASE_URL`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
`GOOGLE_STORAGE_CREDENTIALS`, `GEMINI_API_KEY`, `INTERNAL_WORKER_TOKEN`.

Под:

- портов и HTTP-проб нет: жив ли воркер, видно по логу и очереди; одна реплика;
- пользователь `10001`, не root; корень можно держать только на чтение, если `/tmp` — том на
  запись: там рабочие папки задач и кэш numba (`NUMBA_CACHE_DIR`). Том на диске, не в памяти;
- остановка — SIGTERM: задаче в руках 20 секунд, не уложилась — возвращается в очередь, и процесс
  выходит сам (`queue.md`, «Остановка»); `terminationGracePeriodSeconds` — не меньше 30;
- ffmpeg держится `FFMPEG_THREADS` потоков, сколько бы процессоров ни было на узле: сам он считал
  бы процессоры узла, а не лимит пода, и память росла бы вместе с ними.

Образ — 1,16 ГБ распакованный, ~440 МБ сжатый (amd64). Сколько берёт работающий (измерено
25.09.2026 в Docker, 4 процессора, если не сказано иное):

| | Память | `/tmp` |
|---|---|---|
| покой после старта | ~45 МиБ | — |
| покой после первого ролика (librosa остаётся в процессе) | ~250 МиБ | — |
| превью пяти маленьких файлов (10 процессоров) | пик ~310 МиБ | < 1 МиБ |
| ролик из 5 кусков, 11 с, до TASK-327 | пик 1,1 ГиБ (10 процессоров — 1,45 ГиБ) | ~6 МиБ |

Диск задачи ролика — оценка: все оригиналы воспоминания (api ограничивает их 10 ГиБ) плюс куски,
картинка ролика до наложения звука и готовый ролик; задачи превью — один оригинал (до 1 ГиБ) и его
копии.

## Память сборки ролика

Раньше склейка отдавала все куски ролика одному ffmpeg, и каждый добавлял ~80–100 МиБ: минутный
ролик брал ~3 ГиБ, десятиминутный не собрался бы ни в каком поде. Теперь у каждого куска свой
короткий ffmpeg на два клипа — предыдущий и свой, со склейкой между ними; его кадры идут по трубе в
один кодировщик на весь ролик, а звук кладётся последним проходом, без перекодирования картинки
(`video/assembly.py`). Память от длины ролика не зависит.

Замер 25.09.2026: Docker Desktop (arm64), квота 4 процессора — ffmpeg при этом видит 10, как на
узле. Память — пик суммы процесса воркера и всех его ffmpeg (PSS; ~330 МиБ из неё — сам процесс
с librosa). Материал нарочно тяжёлый: фото 2048×1536 и клипы 4K H.264 с зерном, кусок 2,5 с, под
музыку, `FFMPEG_THREADS` по умолчанию. Время в Docker Desktop плавает на 10–25 % от прогона к
прогону.

| Кусков (длина ролика) | До: память, время | После: память, время |
|---|---|---|
| 5 (10,5 с) | 1,38 ГиБ, 16 с | 0,88 ГиБ, 19 с |
| 15 (30,5 с) | 2,66 ГиБ, 54 с | 0,89 ГиБ, 59–76 с |
| 30 (60,5 с) | убита по памяти на лимите 4 ГиБ | 0,89 ГиБ, 139 с |
| 100 (200,5 с) | не мерилась | 0,89 ГиБ, 543 с |
| 30 с живым звуком, без музыки | не мерилась | 0,95 ГиБ, 159 с |

Ролик целиком — задача `montage` в `run_once`: отсев, ритм, сборка, выкладка; материал — только
фото. «После» — под жёстким лимитом контейнера 1200 МиБ:

| Фото (длина ролика) | До | После |
|---|---|---|
| 5 (10,5 с) | 1,31 ГиБ, 16 с | 0,92 ГиБ, 15 с |
| 30 (60,5 с) | 3,94 ГиБ (впритык к лимиту 4 ГиБ), 46 с | 0,92 ГиБ, 68 с |
| 300 (600 с — самый длинный, что допускает api) | не мерилась | 0,97 ГиБ, 582–627 с |

Счётчик памяти контейнера (`docker stats`, `memory.peak`) показывает больше: в нём кэш страниц
файлов задачи в `/tmp`, который ядро отдаёт по первому требованию, — ролик на 600 с упёрся им в
