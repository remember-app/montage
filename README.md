# montage

Фоновый обработчик Remember. Отдельный процесс на Python, наружу не смотрит: в цикле берёт задачи
из таблицы `jobs` в Postgres, выполняет и почти всё время спит. Единственный способ дать ему работу —
вставить строку в `jobs` (это делает API).

Сейчас он умеет семь вещей: делать превью загруженного медиа (`media_preview`), читать из оригинала
размер кадра, камеру и место съёмки (`media_frame_info`), считать по нему предложение
автоматического отсева (`media_screening`), разбирать, что на кадре и кто на нём
(`media_understanding`), расшифровывать речь в видео (`media_speech`), собирать ролик из материала
воспоминания (`montage`) и раз в час подчищать оборванные загрузки.

## Что нужно

- Python 3.11+
- Postgres 16
- `ffmpeg` и `ffprobe` в `PATH` — ими делаются превью
- Объектное хранилище: локально MinIO из `../api/docker-compose.yml`, в проде Cloudflare R2

## Postgres и хранилище

Канонная локальная база и бакет — те же, что у API, одной командой:

```sh
cd ../api && docker compose up -d
```

Если её ещё нет (или нужна отдельная), сгодится любой Postgres 16:

```sh
docker run --rm -d --name remember-pg \
  -e POSTGRES_USER=remember -e POSTGRES_PASSWORD=remember -e POSTGRES_DB=remember \
  -p 5432:5432 postgres:16
```

## Запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env             # база и локальное хранилище
set -a && . ./.env && set +a     # внести в окружение: воркер читает только его

python worker.py init            # создать таблицы воркера
python worker.py tracks          # выложить музыку в хранилище (ниже, «Треки»)
python worker.py run             # цикл разбора очереди, Ctrl-C для остановки
```

Своего чтения `.env` у воркера нет — переменные приходят из окружения, и на хостинге их задаёт
сам сервис. Имена хранилища — те же четыре, что читает API, так что вместо своего `.env` можно
внести его `../api/.env` целиком.

`init` можно звать сколько угодно раз: `schema.sql` идемпотентен (`CREATE TABLE IF NOT EXISTS`),
на чистой базе накатывается с нуля.

Необязательный `R2_REGION` (по умолчанию `auto`) — на случай хранилища, которому не всё равно,
чем подписан запрос.

`API_URL` и `INTERNAL_WORKER_TOKEN` нужны только готовому ролику — ими воркер стучится в API,
чтобы тот разослал пуш. Не заданы — сборка всё равно проходит, в логе остаётся предупреждение.

## Фиктивная задача

В другом терминале (с тем же окружением):

```sh
python worker.py enqueue dummy         # воркер её возьмёт и поставит done
python worker.py enqueue dummy fail    # ref=fail — упадёт и уйдёт в повтор
```

Второй вариант и есть проверка повторов: воркер отметит попытку, запишет ошибку и отложит задачу
(30 с, потом 60 с), а после третьей попытки поставит `failed`.

## Превью (`media_preview`)

Задачу ставит API, когда байты доехали в хранилище; в `ref` — id строки `media_items`. Воркер
качает оригинал и делает то, что показывает галерея:

| что загрузили | что получается | куда пишется |
|---|---|---|
| фото | миниатюра шириной 640 | `thumbnails/<id>.jpg` → `thumbnail_key` |
| фото | копия JPEG, длинная сторона до 2048 | `previews/<id>.jpg` → `preview_key` |
| видео | постер (кадр с первой секунды) | `thumbnails/<id>.jpg` → `thumbnail_key` |
| видео | копия 720p H.264 + AAC, faststart | `previews/<id>.mp4` → `preview_key` |

Дальше строка становится `ready`, а измеренная длина видео заменяет ту, что заявил телефон.
Оригинал не трогается. Меньше исходника ничего не увеличивается: маленькое фото так и остаётся
маленьким.

Фото на боку не остаётся. EXIF-поворот JPEG ffmpeg применяет сам, а HEIC — нет: портретный кадр
iPhone лежит в файле как кадр сенсора с пометкой `irot` «повернуть», и ffmpeg 7.1 её не читает, так
что миниатюра и крупная копия выходили лёжа на боку. Поэтому HEIC перед превью раскодирует libheif
(`photo.stand_up`, отдельным процессом, как и чтение EXIF) в JPEG без пометки о повороте — уже
развёрнутый, и ffmpeg режет копии из него. Не вышло раскодировать — превью делается из оригинала, как
раньше. Копии, сделанные до этого, сами не пересчитываются: у них нет признака, по которому их можно
найти. Ролик от них не страдает: HEIC при сборке режется из того же развёрнутого файла, а не из
копии и не из оригинала (`montage._back_to_originals`, шаг 2 «Ролика»).

Фото, которое стало `ready` ещё до того, как воркер научился делать крупную копию, догоняется само:
`sweep_photos_without_previews` раз в час ищет `photo` + `ready` + пустой `preview_key` без уже
идущей задачи и ставит `media_preview` заново — на оригинале, который и так лежит в хранилище.
Повторной загрузки от участника не требуется. Задача, которая упала все три раза, следующим часом не
повторяется: её пробуют ещё раз через `CATCH_UP_AFTER_HOURS`, чтобы битый оригинал не молол очередь
круглые сутки, а час недоступного R2 не оставил старые фото без копии навсегда.

Упало — обычные повторы очереди, а после третьей попытки `media_items.status` тоже становится
`failed`, чтобы галерея перестала ждать и показала плейсхолдер.

`media_items` — таблица API (его миграция `004.do.media.sql`), montage только читает и пишет строки
по id. Схему заводят миграции API: `cd ../api && npm run migrate`.

## Размер, камера и место (`media_frame_info`)

Задачу ставит сам воркер — концом `media_preview`, как только строка стала `ready`; в `ref` тот же
id `media_items`. Воркер качает оригинал, меряет картинку и читает то, что записала в файл сама
камера, — для строк «Размер», «Камера» и «Место» листа «Сведения о кадре» (doc-02, макет
`design/screens/SheetFrameInfo.html`). Колонки — в таблице API (его миграции `004.do.media.sql` и
`100.do.frame-info.sql`):

| столбец | что в нём |
|---|---|
| `width`, `height` | размер в пикселях — «4032 × 3024» на листе |
| `camera_model` | модель камеры: `iPhone 15 Pro` (марка «Apple» лежит в EXIF отдельно и не берётся) |
| `focal_length_mm` | фокусное расстояние в мм |
| `aperture` | диафрагменное число: `1.8` — это «f/1.8» |
| `latitude`, `longitude` | координаты съёмки |

**Размер — такой, каким кадр виден человеку.** Телефон, повёрнутый на бок, пишет кадр так, как его
снял сенсор, и рядом — пометку, какой стороной вверх его показывать; в колонки идёт пометка уже
применённая. Снятая боком фотография и вертикальное видео выходят выше, чем шире. У фотографии
поворот лежит в EXIF (`photo.UPENDED`; у HEIC — в `irot`, его применяет сам libheif), у видео — в
display matrix контейнера, её отдаёт ffprobe; ровно её же применяет при раскодировании ffmpeg, так
что превью и ролик видят ту же картинку. С фотографией так не всегда: EXIF-поворот JPEG ffmpeg 7.1.5
из образа применяет (проверено по всем восьми значениям, тест `test_a_jpeg_turned_by_its_exif…`), а
`irot` у HEIC — нет, поэтому превью HEIC делается из уже развёрнутой копии (см. «Превью»).
Померить нечего (в файле вообще нет изображения) — колонки остаются пустыми, задача не падает.

Готовой строкой «iPhone 15 Pro · 24 мм · f/1.8» это не хранится: единицы в ней — слова, и ставит их
приложение на языке читателя. В файле ничего нет — колонки остаются пустыми, и это обычный исход, а
не сбой: скриншот, кадр, пересохранённый редактором, всё, что пришло через мессенджер.

**Место — это координаты.** Названия по ним воркер не ищет и в сеть за ним не ходит: геокодер —
платная служба и запрос с чужим местоположением внутри, а нужно ли продукту название вообще —
вопрос не к воркеру (TASK-191).

У фотографии читается EXIF, у видео — теги контейнера: там телефон пишет модель и координаты
(`com.apple.quicktime.*`, у Android место приходит как `location`), а про оптику не пишет ничего,
так что у видео фокусное расстояние и диафрагма остаются пустыми.

EXIF читается библиотекой (`pillow` + `pi-heif`), хотя всё остальное про файл спрашивается у
ffprobe: EXIF JPEG он отдаёт лишь тегами кадра с дробями текстом, а из HEIC не отдаёт вовсе. HEIC —
то, что грузит iPhone, и от формата файла и от того, какой ffmpeg стоит на хосте, строка «Камера»
зависеть не должна. Фото, которое библиотека не открыла вовсе (`kind` — всего лишь слово телефона о
файле), всё равно меряется ffprobe. Библиотеке отдаются только JPEG и HEIC (`photo.FORMATS`): другие
форматы камера не пишет, а `getexif()` у PNG декодирует картинку целиком (файл в 2 МБ на 169
мегапикселей — секунда и 660 МБ), — их меряет ffprobe, камеры и места у них нет.

Библиотека — это C-код, а байты приходят от участника воспоминания, поэтому читает она в отдельном
процессе (`photo.py`, запускается как скрипт), а не в воркере: HEIC с несколькими испорченными байтами,
из которого ffmpeg ещё делает миниатюру, роняет libheif прямо в `Image.open` (segfault; три файла из
тысячи перебитых). Процесс, который упал, завис дольше минуты (`photo.TIMEOUT_SECONDS`) или ничего не
ответил, — это файл, в котором нечего читать: колонки пустые, размер меряет ffprobe, задача `done`, в
логе предупреждение. Это защита от падения, а не песочница: процесс идёт от того же пользователя, что и
воркер. У `pillow` есть и свой предел на число пикселей (`DecompressionBombError`, около 179
мегапикселей): выше него камера не читается, размер — от ffprobe. А тот на заголовок, который не
принять ни одному декодеру (900 мегапикселей в файле на 900 байт), отвечает нулями — «0 × 0» в
колонки не идёт: размера нет, колонки пустые, задача `done`.

Число, которого не примут ни колонка, ни карта, не записывается: NaN и бесконечность (дробь с нулём в
знаменателе, длинный ряд цифр в теге места), неположительное фокусное и диафрагма, широта за 90° и
долгота за 180° (тег места в градусах и минутах, прочитанный как десятичные градусы) и место ровно
(0, 0) — так место пишет камера, не поймавшая спутники, а сама точка это открытая вода — остаются
пустыми (`media._plausible`). Название камеры — текст из файла, который увидят все участники
воспоминания: непечатные символы из него выбрасываются (NUL колонка `text` не принимает — задача
падала бы три раза и заново каждые сутки), длина — не больше `MODEL_LENGTH`. В лог идёт только то,
что прочитано, — имена колонок, а не значения: координаты — персональные данные, и живут они в базе,
откуда их отдаёт API.

Отдельная задача, а не шаг превью, — чтобы оригинал читался один раз на все строки листа, а догонка
для старого материала стоила скачивания и разбора, а не полной перекодировки.
`sweep_media_without_frame_info` раз в час и при старте ставит задачу готовым медиа, у которых
пустой `width`, — тем же механизмом, что догоняет фото без крупной копии (`_catch_up` в
`worker.py`). Признак «этот файл уже прочитан» — именно размер: пустая камера нормальный ответ и от
непрочитанного файла неотличима, а размер есть у всего, что вообще попало в галерею, — превью
сделано из той же картинки. Упавшую все три раза задачу пробуют ещё раз через
`CATCH_UP_AFTER_HOURS`, как и везде здесь. Так же и файл, у которого размера нет и быть не может
(задача кончается `done`, а `width` остаётся пустым): прочитанное за последние сутки не читается
заново, иначе такой файл скачивался бы и разбирался каждый час, пока работает воркер, — теперь раз в
сутки.

## Предложение отсева (`media_screening`)

Задачу ставит сам воркер — в тот момент, когда строка становится `ready` (конец `media_preview`); в
`ref` тот же id `media_items`. Воркер качает оригинал и зовёт `selection.judge` — ту самую оценку,
которой потом решается, войдёт ли кадр в ролик, — и кладёт её ответ в две колонки, которые API
отдаёт галерее (его миграция `060.do.media-screening.sql`):

| столбец | что в нём |
|---|---|
| `screening_rejected` | `false` — анализ посмотрел и оставил, `true` — отбраковал, `null` — ещё не смотрел |
| `screening_reason` | почему отбраковал: `unreadable`, `blur`, `exposure`; у оставленного — `null` |

Это **предложение**, а не решение (doc-03, «Автоматический отсев брака как предложение»): организатор
видит его в галерее до заказа и правит списками «включить» / «исключить». На сам ролик колонки не
влияют никак — что войдёт, по-прежнему решает `selection.choose` в момент заказа, и пайплайн сборки
эти две колонки не читает вовсе.

`duplicate` сюда не попадает намеренно. Дубль — не свойство файла, а сравнение кадров между собой:
серия снимков в пределах двух секунд, из которой остаётся самый резкий (`selection._dedup` по всему
воспоминанию сразу). Сам по себе файл дублем не бывает, а вердикт, опирающийся на соседей,
переворачивался бы при каждой новой загрузке того же мгновения. Дедуп остаётся там, где он и был, —
в заказе.

У фотографии берётся крупная копия (`preview_key`, длинная сторона 2048), а не оригинал: из неё же
режется кусок в ролике, так что предложение и заказ смотрят на один и тот же файл. Копии ещё нет или
она не отдалась — берётся оригинал. У видео по-прежнему только оригинал: его превью 720p сглаживает
ровно те края, по которым меряется резкость.

Копия — не просто дешевле, она и точнее: swscale не растягивает фильтр дальше примерно 64-кратного
уменьшения, поэтому оригинал в 12032 пикселя, сжатый сразу до 96×54, не усредняется, а
прореживается. Резкость от этого завышалась (алиасинг читается как детали), а экспозиция уезжала —
кадр со средней яркостью 25 мерился как 13 и уходил в брак как «слишком тёмный». Пороги
(`MIN_SHARPNESS`, `LUMA_RANGE`, `CLIPPED_LIMIT`) при переходе на копию не менялись: на реальном
материале вердикты совпали везде, кроме тех кадров, где старое число было артефактом прореживания
(TASK-184).

Медиа, ставшее `ready` до появления этой задачи, догоняется так же, как фото без крупной копии:
`sweep_media_without_screening` раз в час ищет `ready` + пустой `screening_rejected` без уже идущей
задачи и ставит `media_screening`. Файл, который не читается или в котором нет ни одного годного
кадра, получает `unreadable` и успокаивается — «не посчитано» навсегда не остаётся. Недоступное
хранилище — другое дело: это обычные повторы очереди, а после третьей попытки колонки так и остаются
`null` (сказать «брак» о файле, до которого не дотянулись, было бы неправдой) и задача повторяется
через `CATCH_UP_AFTER_HOURS`. Статус самой записи задача не трогает ни при каком исходе: кадр,
который анализ забраковал, остаётся в галерее и скачивается как любой другой.

## Ролик (`montage`)

Задачу ставит API, когда организатор заказал ролик; в `ref` — id строки `montages`, в её `params`
лежит заказ: `target_seconds`, `orientation`, музыка — `music_tracks` (список треков, ниже) и
`music_note` (пожелания к ним словами организатора), необязательный `story_text` (история ролика
словами организатора, её читает только режиссёр, ниже) и, необязательно, два списка id медиа:
`include_media_ids` и `exclude_media_ids` (ниже).

Ролик собирают пять файлов, и граница между ними жёсткая:

| файл | за что отвечает |
|---|---|
| `director.py` | **режиссёр**: план ролика от нейросети — порядок кусков, длина каждого, акцент |
| `selection.py` | **отсев**: что войдёт в ролик, в каком порядке и почему остальное не вошло |
| `rhythm.py` | **ритм**: сколько держать каждый кусок, чтобы склейки попадали в биты трека |
| `assembly.py` | **сборка**: отобранные куски на общий холст и в один файл, `ffmpeg`-ом |
| `montage.py` | оркестратор: читает заказ, качает оригиналы, зовёт модули по очереди, пишет итог |
| `journal.py` | **журнал**: тонкий писатель рассказа о сборке; что записать, решает оркестратор |

Режиссёр и отсев отвечают на один и тот же вопрос и отдают одно и то же: сначала спрашивают
режиссёра, а когда режиссёра нет (нет поставщика нейросети — сегодняшнее состояние), ролик режет
отсев, как резал всегда. В отсеве нет ни одной склейки, в ритме — ни одного кадра, в сборке — ни
слова про резкость, экспозицию и дубли: ей дают готовый список кусков (длительность, откуда резать,
место в ролике) и она их склеивает, не спрашивая, почему именно эти. Любой из них заменяется, не
трогая остальные, — этого и просит спека (doc-03, «Сервис монтажа собран из отдельных модулей»);
тем же швом пришито понимание (`understanding.py`, ниже).

Отсев отвечает на два вопроса по отдельности. `judge` смотрит один скачанный файл: читается ли он,
есть ли в нём годный кадр, где в нём лучший момент. `choose` из оценённых кусков выбирает те, из
которых выйдет ролик. Оба возвращают не только прошедшее, но и отклонённое — с причиной на каждом
куске: `unreadable`, `blur`, `exposure`, `duplicate`, `excluded`, `no_room`. Причины — короткие
коды, а не фразы для человека: их читает код, а показывает их потом приложение своими словами.

Пайплайн — «Montage-пайплайн» из `architecture.md` по шагам:

1. все `ready`-медиа воспоминания из базы; меньше трёх — не собираем (ниже);
2. оригиналы качаются во временную папку, она убирается сама; к каждой **фотографии** рядом
   качается крупная копия из превью (`preview_key`, длинная сторона 2048). Дальше снимок везде
   берётся из неё: и отбор (шаг 3) считает по ней резкость с экспозицией, и кусок режется из неё —
   если её хватает на холст. Не хватило по одной из сторон (панорама) — кусок режется из оригинала,
   хотя вердикт отбора остаётся сделанным по копии: это суждение о картинке, а не о том, в скольких
   пикселях она лежит. Копии ещё нет или она не отдалась — и отбор, и сборка идут по оригиналу, как
   раньше. Видео это не касается ни на одном шаге: его превью 720p — вдвое ниже холста и сглажено
   ровно по тем краям, по которым меряется резкость. И HEIC, у которого режется не копия и не
   оригинал, а развёрнутый libheif файл (`photo.stand_up`): ffmpeg не применяет его `irot`, и
   портретное фото iPhone легло бы в ролик боком — а какая из копий сделана до починки превью, по
   копии не сказать;
3. план режиссёра (ниже), если есть кого спросить, — иначе отбор: кадры видео семплируются раз в
   секунду, размытые (дисперсия Лапласа) и
   пере-/недоэкспонированные (гистограмма) отсеиваются, серия снимков в пределах двух секунд по
   дате съёмки схлопывается в самый резкий кадр (нет даты — файл в дедупе не участвует). Что не
   влезло в `target_seconds` — отсекается по резкости. Порядок в собранном отбором ролике всегда
   хронологический, по дате съёмки, а без неё — по времени загрузки (в ролике по плану порядок
   назначает режиссёр). Файл, который не читается
   или в котором не нашлось ни одного годного кадра, просто не попадает в ролик; годных кусков за
   вычетом исключённых осталось меньше трёх — не собираем. Выбор организатора («включить» и
   «исключить», ниже) этот шаг уважает поверх любой оценки. Отобранного не хватило на заказанную
   длину — куски видео держатся дольше, пока не наберут её (ниже, «Заказанная длина»);
4. каждый **отобранный** кусок нормализуется на общий для ролика холст, H.264, 30 fps, с обрезкой
   по краям. Холст выбирает заказ: 1920×1080 (`landscape`, по умолчанию) или 1080×1920 (`portrait`);
   материал другой формы обрезается, а не получает поля — кадр увеличивается, пока не закроет холст
   целиком, а лишнее срезается по центру: горизонтальное видео на вертикальном холсте теряет края по
   бокам, вертикальное на альбомном — верх и низ, кадр той же формы входит как есть. Чёрных полей в
   ролике нет ни при какой ориентации (человек, 2026-09-21): поля впечатались бы в файл навсегда, а
   не только на тот экран, где ролик смотрят. Обрезка по центру и слепая — куда смотреть, воркер на
   этом шаге не знает. Отбор идёт раньше нормализации (в
   `architecture.md` шаги стоят наоборот) — чтобы не кодировать в 1080p то, что в ролик всё равно
   не войдёт. Фотография декодируется и масштабируется **один раз на кусок**: готовый кадр
   удерживается фильтром `loop` до конца куска. Зацикливание входа (`-loop 1`) заставляло ffmpeg
   перечитывать снимок на каждом кадре клипа, и на снимке 8368×5584 один трёхсекундный кусок
   занимал минуты, а вся сборка вставала (TASK-183);
5. ритм: в собранной дорожке ищутся биты, и длина каждого куска подтягивается к ближайшему — так,
   чтобы на бит попала середина кросс-фейда, то место, где склейка слышна (ниже). Заказ без музыки
   этот шаг пропускает целиком: подгонять склейки не подо что, и куски держатся столько, сколько им
   дали отсев, режиссёр и набор заказанной длины. Длины с этого момента окончательные, и тут же в
   базу уходит раскладка ролика (ниже);
6. сборка: клипы по 4 секунды вокруг лучшего момента (дольше, если ролик добирает заказанную
   длину), фото по 2,5 секунды (неподвижным кадром, без Ken Burns), кросс-фейд 0,5 секунды между
   кусками, сверху дорожка с fade in/out. Звука исходников в ролике с музыкой нет — только музыка;
   ролик без музыки идёт с живым звуком самих видео (ниже);
7. файл уезжает в `montages/<id>.mp4`, а обложкой — миниатюра шириной 640 в `montages/<id>.jpg`:
   кадр лучшего момента первого куска, а не нулевой кадр ролика. Кусок режется с центром на этом
   моменте, поэтому начинается он раньше — у клипа с телефона там сплошь и рядом чернота, а
   обложке черноты нельзя; строка становится `ready` с обоими ключами и длительностью, и воркер
   стучится в `POST {API_URL}/internal/montages/<id>/ready`, чтобы API разослал пуш. Кадр вырезать
   не удалось — ролик всё равно готов, `poster_key` остаётся пустым и API отдаёт `poster_url: null`,
   как у роликов, собранных до появления постеров;
8. временные файлы убираются вместе с папкой.

**Раскладка ролика** — где в нём стоит каждый вошедший кадр: строка с секундой начала и
длительностью в `montage_frames` (таблица API, его миграция `100.do.frame-info.sql`), по строке на
каждое **появление**, а не на кадр — один файл законно стоит в ролике дважды (клип, разрезанный
надвое; фото, вернувшееся в конце). `start_seconds` — секунда, с которой кадр начинает проявляться
(начало перехода к нему); полностью он виден с `start_seconds` + 0,5. Пишется она дважды: сразу после подгонки в ритм, когда длины
кусков окончательные, — чтобы место кадра было видно, пока ffmpeg ещё кодирует, а это минуты, — и
ещё раз по нормализованным клипам, длину которых сборка измеряет, а не берёт на слово. Каждая запись
заменяет строки ролика целиком, а каждая попытка сборки начинается с того, что стирает раскладку
прошлой — там же, где начинает журнал с чистого листа (ниже, «Повтор»): раскладка живёт и умирает
вместе с журналом своей попытки, и до ритма у ролика её нет вовсе.
Не записалась — предупреждение в лог, и сборка идёт дальше: минуты кодирования не выбрасываются
из-за одной вставки, а ролик, которого нет в списке у своих кадров, — это пропуск в списке, а не
пропавший ролик. Читает таблицу только API, дважды: «в каких роликах этот кадр и на какой секунде»
на листе «Сведения о кадре» (doc-02) — только у готовых роликов, — и места кадров в журнале монтажа,
у ролика в любом статусе. Таблица общая на все вехи — второй копии раскладки в чужом журнале быть не
должно.

**Заказанная длина** — `params.target_seconds`, до десяти минут. Предел считает API
(`materialLeft` в его `src/montages/montages.ts`): сумма всех видео плюс 2,5 секунды на каждое фото
минус 0,5 секунды на каждую склейку — склеек на одну меньше, чем кадров, — вниз до целой секунды и
не больше 600. То есть длина ролика из всего материала целиком, по тем же 2,5 секунды на фото и 0,5
на склейку, что держит воркер. Заказанная длина — обещание, а не пожелание: пока материала хватает,
ролик выходит заказанной длины с точностью до подтяжки склеек к битам — проценты, а не секунды.
Ролик без музыки (пустой список треков, ниже) не подтягивается ни к чему: там заказанная длина
держится ровно, пока недостающее могут добрать клипы, — о переборе на последнем фото ниже.

Набирается она так. Базовые длины — фото 2,5 с, клип 4 с вокруг лучшего момента. Сначала в ролик
добирается неиспользованный материал: и отбор, и режиссёр останавливаются на куске, который в заказ
уже не влезает. Если и всего годного материала мало, куски **видео держатся дольше**
(`selection.stretch`): не хватающие секунды делятся между клипами поровну, начиная с самого
короткого файла, — что один клип не может дать, отдают остальные, — и каждый растягивается вокруг
того же лучшего момента максимум до целого файла. **Фото не растягиваются**: застывший на минуту
кадр — это не длинный ролик, а остановленный. Склейки в счёт входят: каждая съедает полсекунды, и
длина считается по собранному ролику (`assembly.length_of`), а не по сумме кусков.

Подрезать фото тоже нельзя: к ролику оно добавляет две секунды (2,5 минус склейка) или ничего, а
заказ — целые секунды. Поэтому, когда добрать недостающее клипами нельзя — их нет или каждый уже
целиком, — отбор (`selection.choose`) всё-таки берёт самое резкое из не влезших фото, если с ним
ролик ближе к заказу, чем без него; перебор тогда всегда меньше секунды. Так заказ на предел
получает все кадры: k фото — это ролик 2k + 0,5 с, а заказать можно 2k, — и 40 фото на заказ 80 с
дают 80,5 с из всех сорока, 3 фото на 6 с — 6,5 с из трёх. Пока хоть один клип может держаться
дольше, перебора нет: недостающее добирают клипы. План режиссёра так не добирается — длины кадров в
нём назначает он сам.

Шаг общий для обоих способов режиссуры — `montage.py` зовёт его и после `director.direct`, и после
`selection.choose`, так что план нейросети дотягивается до заказа тем же способом и мимо этого шага
не пройти. Потолки куска (`rhythm.MAX_PIECE_SECONDS`, `director.MAX_PIECE_SECONDS`) ограничивают,
сколько кусок может получить от плана и от битов, но растянутый кусок обратно не срезают: ритм
двигает его в его собственных границах.

Материала меньше заказанного — ролик просто выходит короче, сколько есть: это не ошибка и не повод
для повтора. Ради длины ничего не возвращается: ни исключённое организатором, ни отсеянное отбором,
ни один кусок дважды.

**Выбор организатора** — `include_media_ids` и `exclude_media_ids` в `params`, списки id из
`media_items`, оба необязательные. Отмеченное «исключить» не попадает в ролик никогда, каким бы
резким ни было. Отмеченное «включить» попадает всегда, если файл технически пригоден — читается и
в нём есть хоть один кадр, — даже когда алгоритм счёл кадры браком; не отменяет «включить» только
файл, в котором кадра нет вовсе, и это не мнение, а отсутствие картинки. Время под «включить»
тратится первым, и остальной отбор подстраивается под остаток `target_seconds`. Названное в обоих
списках сразу остаётся за бортом: заказать ролик заново можно, вынуть кадр из готового — нет.

**Музыка заказа** — `music_tracks` в `params`: список треков любой длины, в том порядке, в каком
они играют. Элемент списка — либо id трека полки (`assembly.TRACKS`), либо ключ файла, который
организатор загрузил сам (ниже, «Свой трек»); отличаются они ключом — своё лежит под `music/<uuid>`.
Полка и свои мешаются в одном списке свободно. Из списка собирается **одна дорожка**: треки идут
друг за другом в заданном порядке, стык проходит коротким фейдом (`assembly.TRACK_FADE_SECONDS`,
секунда), и дальше эта дорожка живёт как один трек — в ней ищется ритм, она подгоняется под длину
ролика. Один трек в списке не пересобирается вовсе: его файл и есть дорожка.

**Пустой список — это «без музыки»**, и тогда ролик идёт с живым звуком самих видео (макет
`design/screens/MontageMusicNone.html`, «Только живой звук из видео»): у клипов остаётся их
собственная дорожка, фотографии и клипы, снятые без звука, звучат тишиной, а склеивается звук тем
же перехлёстом, что и картинка (`acrossfade` в полсекунды против `xfade` в те же полсекунды), так
что звук и изображение не расходятся ни на одной склейке. Края ролика гаснут тем же полусекундным
фейдом: звук, оборванный на полуслове, щёлкает. Ритма в таком ролике нет — см. шаг 5.

**Заказ старой формы** — `music_tracks` в `params` нет вовсе — читается как читался: свой трек
`music_track_key`, иначе трек полки `music_track_id`, иначе «тёплая» по умолчанию. Это повтор
ролика, заказанного до появления списков: его строка лежит в базе как её записали, и собраться она
должна как собиралась.

**Пожелания к трекам** — `music_note`, текст словами организатора: «как использовать треки». Читает
его только режиссёр (ниже) — дорожку он не перекраивает ни на секунду, а порядок и длина кусков
могут лечь под него. Поставщика нейросети нет (сегодняшнее состояние, decision-10) — пожелания не
влияют ни на что, ролик собирается ровно так же.

**Треки полки** — пять, те же и в том же порядке, что на экране «Под что монтировать»
(`design/screens/MontageMusic.html`): `bright` — «Яркая», `warm` — «Тёплая», `calm` — «Спокойная»,
`night` — «Ночь», `road` — «Дорога». Файлы лежат в `tracks/<id>.mp3`, откуда каждый взят и под какой
лицензией — в `tracks/README.md` там же. Все пять написал Kevin MacLeod, все пять взяты с
incompetech.com под Creative Commons Attribution 4.0: **указание автора обязательно там, где ролик
показывают**, строки для этого лежат в том же `tracks/README.md`. Трек короче ролика играет с начала
ещё раз, длиннее — обрывается вместе с картинкой.

Ролик режется из файла на диске, а вот **послушать** трек до заказа («Послушать» на экране «Под что
монтировать») можно только из хранилища: диск воркера не виден ни API, ни приложению. Поэтому те же
пять файлов выкладываются в бакет под ключами `tracks/<id>.mp3` — тем же id, что в `assembly.TRACKS`:

```sh
python worker.py tracks          # нужны только четыре переменные хранилища, база не нужна
```

Команду зовут на выкатке, звать можно сколько угодно раз: лежащее в бакете не перезаливается
(проверяется `head_object` по каждому ключу), в ответе — сколько из пяти реально ушло. **Новый
трек** — файл в `tracks/`, строка в `assembly.TRACKS`, такая же строка у API (он не даст заказать
трек, которого нет у него в списке) и ещё один `python worker.py tracks`. **Замена** файла под тем
же id — единственный случай, когда команды мало: объект под этим ключом уже есть, и его сначала надо
удалить из бакета (`aws s3 rm`, консоль R2, `mc rm` у MinIO), иначе в приложении так и будет играть
старое.

**Свой трек** — ключ `music/<uuid>` аудиофайла, который организатор загрузил сам (API, таблица
`music_uploads`, его миграция `060`): в списке `music_tracks` вперемешку с полкой, в заказе старой
формы — в `music_track_key`. Воркер качает его из того же бакета и дальше не различает свой трек и
библиотечный — ритм ищется и склейки ложатся одинаково. В старой форме заказ с обоими полями сразу
API не пропускает; если такой всё же дошёл, воркер берёт свой трек. Файл, который не открывается,
в котором нет звука (API принимает под трек любые байты — фотографию, немой клип) или который
оказался плейлистом, а не музыкой, — отказ без повторов.

**Ритм** — склейки попадают в биты дорожки, а не режутся ровными кусками. В дорожке ищутся биты
(`librosa`, лицензия ISC — она же в doc-11), и длина каждого куска подтягивается так, чтобы на бит
пришлась середина кросс-фейда: именно там склейка слышна. Подгоняется длина уже выбранного куска —
что вошло в ролик и в каком порядке, от музыки не зависит; поэтому неважно, услышала библиотека
пульс на четвертях или на восьмых: частая сетка двигает кусок меньше, редкая больше. Фотографию
можно держать сколько нужно, клип — только пока в его файле есть что показывать, дальше упор.
Последний кусок не трогается: за ним конец ролика. Ролик от этого выходит около суммы кусков, а не
ровно в неё — на полбита в ту или другую сторону; заказанную длину это не отменяет, она держится с
точностью до этой подтяжки (выше, «Заказанная длина»).

Ищется ритм по всей собранной дорожке, а не по первому её треку: склейки идут в такт всему списку,
и там, где один трек сменяется другим, сетка сменяется вместе с ним. Разбирается она не дальше
получаса (`rhythm.HORIZON_SECONDS`): дальше ничего не играет, а час музыки — около двух гигабайт
памяти на разбор. Ролик без музыки этот шаг пропускает целиком — биты искать не в чем.

Дорожка без выраженного темпа (ровный гул, шум, запись голоса) — понятный фолбэк: биты не
находятся, куски остаются как были, ролик собирается ровными кусками. Тем же кончается и трек,
который не удалось разобрать: разбор музыки не может уронить ролик.

**Оценка кадра** — пока только резкость. `architecture.md` просит ранжирование NIMA (ONNX, CPU);
модель, её происхождение и лицензия — открытый вопрос, и до ответа кадры сортируются по уже
посчитанной дисперсии Лапласа. Место помечено в коде (`selection.py`, `_best_moment`): меняется
одна функция, пайплайн вокруг остаётся.

Отказы без повторов: материала меньше трёх файлов, годного материала меньше трёх, весь материал
исключён организатором, неизвестное название трека (ни id полки, ни ключ `music/<uuid>` — в списке
`music_tracks` или в старом `music_track_id`), свой трек, которого нет в бакете (404 / `NoSuchKey`),
нечитаемый свой трек и неизвестная `orientation`. Во всех семи воркер сам ставит
`montages.status='failed'` с текстом причины и штатно завершает задачу — на второй попытке ответ был
бы тот же. Всё остальное (упал `ffmpeg`, хранилище недоступно или не ответило вовремя, нет файла
кадра) — обычные повторы очереди, а после третьей попытки строка тоже становится `failed`, и у
организатора появляется «повторить».

`montages.error_text` API отдаёт всем участникам воспоминания, поэтому туда идёт короткая фраза для
человека, а не текст исключения: подробности (стек, вывод `ffmpeg`, адрес хранилища) остаются в
`jobs.last_error` и в логе, которые читает не пользователь, а тот, кто чинит.

`montages` — таблица API (его миграция `020.do.montages.sql`), montage только читает и пишет строки
по id; `montage_frames` (его миграция `100.do.frame-info.sql`) montage только пишет.

### Журнал монтажа — что и когда пишется

Пока ролик собирается, воркер рассказывает о сборке: пять этапов и реплики на каждом — что за кадр
в руках, что на нём видно, берём или мимо и почему (doc-03, «Монтаж в прямом эфире»; экраны
`design/screens/MontageLive.html`, `MontageLiveStage.html`, `MontageLiveDone.html`). Рассказ лежит
вместе с роликом и читается когда угодно после сборки.

Уговор тот же, что и с самим роликом: **схему завёл API** (его миграция `130.do.montage-journal.sql`,
контракт колонок — в его README, раздел «Журнал монтажа»), **содержание пишет воркер**, а отдаёт
приложению снова API. Схему воркер не меняет и не заводит.

Пишет журнал **только оркестратор** (`montage.py`) — по тому, что вернули модули; отсев, режиссёр,
ритм и сборка о журнале не знают ни строчкой, иначе замена любого из них тащила бы за собой рассказ
о нём. `journal.py` — тонкий писатель: открыть этапы, добавить запись, подвинуть счётчик, закрыть
этап. Слов для человека в базе нет — идут коды и числа (`skip`, `blur`, «1 из 4»), фразу из них
строит приложение на своём языке; исключение одно — описание кадра и мысль модели, это её
собственные слова.

| Этап | Записи по ходу | Итог этапа (`outcome`) |
|---|---|---|
| `screening` | на каждый отсеянный файл: «мимо» и код причины (`unreadable`, `blur`, `exposure`) | `kept`, `of`, `reasons` — «212 из 214 годятся» |
| `understanding` | на каждый файл с сохранённым описанием: описание и метки «кто в кадре» | `described`, `of`, `faces`, `people`, `animals` — «37 лиц, 5 людей в главных» |
| `directing` | на каждый кадр, о котором этому этапу есть что сказать: «беру» или «мимо» со своей причиной; у видео — какой кусок исходника взят. Ролик режиссировала нейросеть — её словами: мысль о плане в целом, мысль о кадре, часть истории, рамка «куда смотрит» | `frames`, `of`, а у нейросети ещё `parts` и `part_titles` |
| `rhythm` | — | `track` (треки в порядке заказа), `bpm`, `cuts` — сколько кусков сдвинулось |
| `assembly` | — | `cuts` (склеек), `seconds` (длина ролика) |

Счётчик «сделано N из M» двигают два этапа, у которых есть что двигать: отсев — по отсеянному
файлу, склейка — по готовому куску. Остальные считаются мгновенно и просто закрываются итогом.
Счётчики «взял N / мимо N / мысли N» воркер не пишет вовсе: их считает API по самим записям.

Подробности, которые не видны из таблицы:

- **Серия одинаковых кадров — одна запись**: «взял 1 из 4» на том кадре, который за серию остался
  (`series_size` ставит сам дедуп, `selection._dedup`). Три строки «мимо, дубль» рядом рассказывают
  то же самое трижды. Одинаково на обоих путях: серию прорежает тот же дедуп и перед вопросом
  модели (`director.direct`), и размер серии едет до журнала на самом куске.
- **Каждое «мимо» — один раз, на своём этапе**: смазанный, тёмный и нечитаемый кадр рассказан
  отсевом, и на режиссёрском этапе его нет вовсе — хотя `selection.choose` возвращает всё, чего в
  ролике нет, вместе с ними. Причины режиссёрского этапа — только его собственные: `duplicate`,
  `no_room`, `excluded`, `left_out`; иначе один кадр шёл бы «мимо» дважды, и счётчик «Мимо N» на
  экране был бы завышен.
- **Слово организатора видно с обеих сторон**: `excluded` причиной на вычеркнутом, `included` — на
  том, что он велел взять. Это единственный код в словаре причин, которым помечено взятое; кадр, у
  которого отсев уже сказал своё «мимо», второй раз вычеркнутым не объявляется.
- **Лица и люди — разные числа**: `faces` — сколько раз человек попал в кадр (сумма меток людей по
  всем разобранным кадрам), `people` и `animals` — скольких воспоминание узнало всего, по разным
  меткам. Один и тот же «человек-1» на двадцати кадрах — это двадцать лиц и один человек.
- **Ритм ролика без музыки** проходит и честно говорит, что дорожки нет: список треков пуст,
  сдвинутых кусков ноль. С музыкой в итоге стоят те же названия, что в заказе (id полки и ключи
  своих треков — называет их приложение), в том же порядке.
- **Разбор кадров ничего ни у кого не спрашивает**: описания пишет `media_understanding` задолго до
  заказа, здесь они только читаются. Ни одного описания — этап проходит и говорит «0 из M», и это
  сегодняшнее состояние продукта, пока ключа от модели нет (decision-10), а не пропущенный шаг.
- **Место кадра в ролике журнал не хранит**: раскладка лежит в `montage_frames` (выше), API
  присоединяет её к записям сам.
- **Режиссёр-нейросеть рассказывает о себе сам** — ниже, «Что рассказывает режиссёр-нейросеть».

**Оценка времени** заводится вместе с этапами, в первую секунду сборки: по числу файлов и
заказанной длине. Ручка — `journal.ESTIMATE`, по паре чисел на этап (секунд на файл, секунд на
секунду готового ролика), и подстраивать её по реальным прогонам надо там: больше оценка нигде не
считается. Сумма по пяти этапам держится равной тому, чем API обещает «соберём за N минут» на итоге
заказа (`estimateMinutes`): **3 с на кадр и 1,5 с на секунду ролика**. Двигать их надо вместе —
иначе обещание перед «Начать монтаж» и «осталось ≈» на экране монтажа разъедутся; сумма пинится
тестом. У идущего этапа «осталось» пересчитывается по факту — потраченное время на сделанное, — а у
закрытого стоит ноль, и сколько он занял, видно по `started_at` и `finished_at`.

**Живьём, а не пачкой в конце.** Приложение опрашивает журнал раз в секунду-две, поэтому каждая
запись уходит отдельной командой и ложится в базу сразу: соединение воркера в автокоммите, никакой
транзакции вокруг сборки нет, и читающий видит запись до конца этапа. Отсюда же и размер записей:
запись на отсеянный файл, одно небольшое `UPDATE` на готовый кусок — и ничего на каждое движение
ffmpeg.

**Повтор** того же ролика (ретрай задачи или «повторить» упавшего) начинает журнал с чистого листа:
старые реплики удаляются, этапы возвращаются в ожидание с новой оценкой, а вместе с репликами
уходит и раскладка прошлой попытки (выше) — иначе места кадров в журнале новой попытки были бы
местами из ролика, которого уже нет. **Упавший ролик** журнал
оставляет как есть — до какого места дошёл, видно, — а этап, который шёл в тот момент, помечается
упавшим; помечается он там же, где ролик называют упавшим (`montage.give_up`), так что ролику,
которому очередь даст ещё две попытки, этап остаётся идущим.

**Журнал — зрелище, а не суть.** Ни одна запись не стоит того, чтобы уронить сборку: всё, что
пишется в журнал, ошибку проглатывает и оставляет строку в логе (`journal.quiet`), а ролик
собирается дальше — как и с раскладкой кадров.

### Что рассказывает режиссёр-нейросеть

Ролик, который режиссировала модель, наполняет режиссёрский этап её собственными словами. Просит их
тот же единственный запрос, которым строится план (`ai.PLAN`), — расширенный, а не новый: план
**без** новых полей (записанный до них ответ) разбирается ровно так же, просто рассказывать по нему
нечего, а `accent` старой формы читается как мысль о кадре.

```json
{"overview": "План на две части: сборы за столом, потом торт — на нём и держим финал.",
 "plan": [{"media_id": "…", "seconds": 3.5,
           "thought": "Вносят торт — главный момент вечера, держу подольше.",
           "part": 2, "part_title": "Торт",
           "focus": {"x": 0.3, "y": 0.05, "w": 0.25, "h": 0.5}}],
 "left_out": [{"media_id": "…", "reason": "собака не про этот вечер"}]}
```

| Из плана | Куда в журнале |
|---|---|
| `overview` | первая запись этапа: `thought` без кадра — мысль про план в целом |
| `thought` | `thought` записи об этом кадре |
| `part`, `part_title` | `story_part`, `story_part_title`; ими же считается итог этапа `parts` и `part_titles` |
| `focus` | `focus_x`, `focus_y`, `focus_w`, `focus_h` — долями кадра |
| `left_out[].reason` | `thought` у «мимо» с кодом `left_out`: причина в журнале — код, и слова в ней приложение показало бы как «не подошёл» |

**Записан каждый кадр, который модели показали**: вошёл в ролик — «беру» с мыслью, частью и куском
исходника; не вошёл — «мимо» с кодом `left_out` и её словами о причине мыслью, или с кодом
`no_room`, если кадр планировали, но он не влез в заказанную длину. Отсеянного и съеденного
дедупом модель не видела, и на этом этапе их нет: о первом уже рассказал отсев, второй рассказан
«взял 1 из N» (ниже). Вычеркнутого она не видела тоже, но он идёт «мимо» с кодом `excluded`, как на
пути без нейросети: кроме этой записи, о нём не рассказал бы никто. «Включить»
организатора остаётся «беру» при любом плане, и причина у него его же — `included`. А кадр,
оставшийся от серии одинаковых, несёт её размер — «взял 1 из 4»: серию прорежает дедуп отсева ещё
до вопроса модели, и её размер едет с куском до журнала, как и на пути без нейросети.

**Ответ модели — недоверенный ввод**, а мысль увидят все участники воспоминания. Читается он у самой
двери (`ai._planned`), и до журнала доходит только то, что выдержало чтение: кусок, которого модели
не показывали, отбрасывается (`director`), «часть» не номером — не часть, рамка не из четырёх долей
внутри кадра — не рамка (выбрасывается целиком, мысль при этом остаётся). Длину и служебные символы
держит сам журнал (`journal._fit`): всё, что модель говорит, идёт в базу через него.

**Потокового ответа по токенам нет** и не планируется: модель отвечает целиком, записи ложатся сразу,
как ответ пришёл, порядком плана, а «печатается вживую» рисует приложение по уже полученной фразе.

## Облачная нейросеть (`ai.py`)

Три вопроса, которые воркер задаёт облачной модели: что происходит в кадре и кто на нём,
что сказано в видео, и в каком порядке из кусков складывается ролик. Задаются они через `ai.AI` —
других дверей к нейросети нет, и код, который спрашивает, не знает, кто отвечает:

```python
brain = ai.AI(conn)                                   # поставщика берёт из окружения
about = brain.describe_media([ai.Blob("image/jpeg", data)], cast=["человек-1"], ref=item_id)
```

Поставщик — переменной окружения, вместе с ключом и (необязательно) моделью:

| переменная | что в ней |
|---|---|
| `AI_PROVIDER` | `gemini` или `openai` |
| `GEMINI_API_KEY` / `OPENAI_API_KEY` | ключ выбранного поставщика |
| `GEMINI_MODEL` / `OPENAI_MODEL` | модель, если не устраивает та, что по умолчанию |
| `OPENAI_TRANSCRIBE_MODEL` | у OpenAI речь расшифровывает отдельная модель отдельной ручкой |

Не задано ничего (сегодняшнее состояние — ключа от человека ещё нет) — воркер **в сеть не идёт**:
каждый вызов пишет в лог, что он пропущен и никто ничего не отвечал, и возвращает `None`. Вызывающий
код на `None` откатывается к тому, что воркер умеет сам, — ролик собирается сегодняшним отбором.
Строка при старте (`cloud model: …`) говорит, есть модель или нет.

Различий между поставщиками два, и оба спрятаны внутри адаптеров: Gemini берёт видео целиком, а
OpenAI видео не принимает вовсе — клип ему описывают вырезанными кадрами (он об этом говорит
ошибкой); речь у Gemini — тот же запрос с аудио, у OpenAI — загрузка файла в свою ручку.

**Новый поставщик** — класс с `name`, `generate` и `transcribe` и одна строчка в `PROVIDERS`.
Ключ и модель он получит из `<ИМЯ>_API_KEY` и `<ИМЯ>_MODEL` сам.

### Журнал запросов

Каждый вызов через `ai.AI` ложится в таблицу `ai_requests` — строка заводится **до** обращения к
модели и закрывается ответом, так что упавший на полпути воркер всё равно оставляет запись о том,
что спрашивали. Наружу её никто не отдаёт, смотреть — руками:

```sh
psql "$DATABASE_URL" -c "select created_at, provider, operation, ref, status, took_ms,
  request->>'prompt', response from ai_requests order by id desc limit 20"
```

`status` — `sent` (спросили, ждём), `answered`, `failed` (в `error` — что пошло не так) и `skipped`
(поставщика нет, никого не спрашивали; `response` у такой строки пустой всегда). В `request` лежит
промпт и по строчке на каждый приложенный файл — тип и размер. Байтов медиа там нет намеренно:
оригиналы и так в хранилище, а копия материала в jsonb сделала бы эту таблицу самой большой в базе.
Ключа там нет тем более.

Две строки `failed`, которые читаются не сразу. «Не ответил JSON-объектом» — это и проза вместо
объекта, и `NaN` с `Infinity`: их принимает Python и не принимает `jsonb`, так что пропусти мы такой
ответ дальше — он сломал бы запись в этот самый журнал уже после того, как за него заплатили.
А `HTTP Error 30x` — это редирект, за которым мы намеренно не идём: urllib унёс бы вместе с ним
заголовок с ключом туда, куда редирект показывает. Того же рода `\u0000` в ответе — `jsonb` не
берёт и его, — но он не стоит целого ответа: невидимый символ просто выбрасывается, а ответ едет
дальше.

## Понимание кадров (`media_understanding`)

Задачу ставит сам воркер — концом `media_preview`, как только медиа стало `ready`; в `ref` — id
строки `media_items`. Облачная модель (через `ai.py`) отвечает одним-двумя предложениями, что
происходит в кадре, и списком действующих лиц — кто в нём есть. Ответ ложится в свою таблицу
`media_understandings` по id медиа и больше не пересчитывается: описанный кадр повторно в нейросеть
не уходит ни при втором ролике, ни при часовой докатке (doc-03, «Второй ролик из тех же медиа не
описывает заново уже описанные кадры»).

| столбец | что в нём |
|---|---|
| `media_id` | id строки `media_items`, одна строка на медиа |
| `memory_id` | чьего воспоминания метки ниже |
| `description` | что происходит в кадре |
| `cast_labels` | кто в кадре — метками этого воспоминания |

**Одни и те же люди и животные** узнаются самой моделью, своей системы распознавания у нас нет
(decision-9). Работает это так: перед каждым следующим кадром воспоминания из таблицы берутся все
метки, которые это воспоминание уже раздало («человек-1», «животное-1»), и уходят в запрос —
модель либо узнаёт кого-то из них, либо заводит следующего по счёту. Поэтому и задача на один
файл: состав растёт по кадру за раз. Метки стабильны внутри воспоминания и за его пределами не
значат ничего — «человек-1» в двух разных воспоминаниях это два разных человека.

**В модель уходит не оригинал**, а копии, которые сделал `media_preview`: фото — крупной копией,
видео — тремя кадрами из 720p-превью, вырезанными равномерно по клипу (края не берём: первый кадр
у телефонного видео сплошь и рядом чёрный). Кадрами, а не клипом целиком, хотя Gemini клип берёт:
OpenAI видео не принимает вовсе, а Gemini считает клип по его длине (258 токенов в секунду,
doc-11) — три кадра отвечают «что происходит и кто в кадре» у обоих поставщиков по цене трёх фото.
Движение при этом теряется, место помечено в коде (`understanding.py`).

Поставщик не настроен (сегодняшнее состояние) — **не описывается ничего**: задача завершается
штатно, в таблицу и в журнал не пишется ничего, кадр остаётся неописанным. Появится ключ —
`sweep_media_without_ai_answers` раз в час находит готовые медиа без описания и ставит задачу сама
(см. «Докатка того, о чём модель не спросили» ниже).

## Речь в видео (`media_speech`)

Задачу ставит сам воркер — в конце `media_preview`, когда видео стало `ready`; в `ref` — id строки
`media_items`. Оригинал качается из хранилища, `ffmpeg` вынимает из него звук (моно, 16 кГц, AAC:
примерно это модель и слушает, а байтов в разы меньше), и расшифровка запрашивается через `ai.AI`.
Сказанное ложится в свою таблицу `media_speech`, одной строкой на медиа:

| столбец | что в нём |
|---|---|
| `media_id` | id строки `media_items` |
| `transcript` | слова, как они сказаны; пусто — речи в записи нет |
| `created_at` | когда расшифровали |

Кто говорит — не спрашиваем и не храним (decision-11): расшифровка ни к кому в кадре не
привязывается, и столбца под это в таблице нет.

Считается один раз: задача на уже расшифрованном видео ни в какую нейросеть не идёт и сразу
завершается — второй и следующие ролики из того же материала берут сохранённое (doc-03). Видео без
звуковой дорожки и видео, в котором никто не говорит, получают пустую расшифровку: это ответ, а не
пробел, и больше их никто не спрашивает.

Пока поставщик нейросети не настроен (сегодняшнее состояние — ключа нет), задача ничего не пишет и
штатно завершается: клип расшифруется, когда ключ появится, — та же часовая докатка, что и у
описаний, ставит задачу сама.

## Докатка того, о чём модель не спросили

`sweep_media_without_ai_answers`, раз в час и сразу при запуске воркера: готовые медиа без описания
в `media_understandings` и готовые видео без расшифровки в `media_speech` ставятся в очередь сами.
Обе задачи ставятся при загрузке — и теряются одинаково. Либо медиа стало готовым, когда ключа ещё
не было: задача честно ничего не записала. Либо модель отказала — бесплатный тариф отвечает «429» на
каждый вызов, три попытки сгорают за минуту, и задача `failed` навсегда. Дальше за этот кадр не
придёт никто: заказ ролика ничего не описывает, он только читает уже посчитанное (doc-03), так что
у воспоминания может остаться 86 упавших описаний и ИИ-монтаж, который не включится никогда, сколько
ролик ни перезаказывай. Докатка — то, что за ними возвращается.

Схема общая с докаткой фото без крупной копии и предложений отсева (`_catch_up` в `worker.py`):
`queued` и `running` не дублируются, а упавшую все три раза задачу трогают не раньше чем через
`CATCH_UP_AFTER_HOURS` — иначе кадр, который модель не может прочитать, уходил бы к ней трижды в
час, а это уже не процессор, а деньги. Через сутки пробуем ещё раз: за сутки лимит тарифа
обнуляется, недоступное хранилище чинится, а платный ключ, поставленный вечером, подхватывается сам.

Нет настроенного поставщика — докатка не делает ничего и ни на что не жалуется: спрашивать некого,
очередь пустая, в журнале только строка самого `ai.py` о том, что поставщик не задан. Свои строки
она пишет, только когда есть что ставить:

```
INFO queued a description for 86 media item(s) that had none
INFO queued a transcript for 4 clip(s) that had none
```

## Режиссёр (`director.py`)

Своей задачи в очереди у него нет: он живёт внутри сборки ролика и спрашивается там, где раньше сразу
звали отсев. Нейросеть получает всё, что пайплайн уже знает о материале, и строит **план ролика**:

| что уходит в запрос | откуда |
|---|---|
| описание каждого кадра и кто в нём | `media_understandings` (`understanding.py`) |
| что сказано в клипе | `media_speech` (`speech.py`), первые 400 символов |
| сколько секунд этот файл вообще может дать | измеренная длина видео; фото — сколько попросят |
| история ролика словами организатора | `params.story_text` из заказа |
| запрошенная длина | `params.target_seconds` |
| пометка «этот кусок обязателен» | `params.include_media_ids` |
| дорожка: треки по порядку и длина каждого | собранная музыка заказа (`params.music_tracks`) |
| пожелания к трекам словами организатора | `params.music_note` из заказа |

Свой трек уходит в запрос словами «свой трек», а не ключом: ключ в бакете модели ничего не говорит,
а оплачивался бы в каждом запросе. Музыка в запросе — то, подо что режиссёр кладёт порядок и длину
кусков; саму дорожку он не перекраивает, она собрана до вопроса. Пустой список музыки — ролик с
живым звуком видео, и это режиссёр тоже видит.

В ответ — порядок кусков, длина каждого и слова режиссёра о том, что он делает: мысль о плане в
целом и о каждом кадре, часть истории, рамка «куда смотрит», причина для того, что осталось за
бортом. Порядок и длину берёт сборка, слова уходят в журнал монтажа («Что рассказывает
режиссёр-нейросеть» выше), а ответ целиком, как и всякий, остаётся в `ai_requests`. Расшифровки
режутся по 400 символов намеренно: всё воспоминание едет в одном запросе, и десять минут речи с
одного клипа оплачивались бы словом.

**Серия кадров уходит в запрос одним кадром.** Перед тем как собрать вопрос, материал проходит тот же
дедуп, что и отбор: снятое в пределах двух секунд по дате съёмки схлопывается в самый резкий кадр, а
если в серии есть «включить» — в названный организатором (нет даты съёмки — файл в дедупе не
участвует). Иначе режиссёр видит всю серию подряд и может поставить два кадра одной секунды рядом,
да и каждый дубль оплачивается в запросе.

**Выбор организатора режиссёр соблюдает так же, как отсев**, и это то же самое правило, записанное
во втором месте. «Исключить» в запрос не попадает вовсе — модель этого кадра просто не видит, и
назвать его не может; если всё-таки назовёт (чужой id, свой же id дважды) — такой шаг плана
выбрасывается. «Включить» уходит пометкой `must_include`, а если план его всё равно забыл — кусок
дописывается в конец плана. Не отменяет «включить» только файл, в котором нет ни одного кадра.

Длину каждого куска режиссёр назначает сам, в пределах от секунды до восьми: клип при этом никогда
не берётся длиннее, чем он есть, и режется по-прежнему вокруг лучшего момента (`selection.cut_to`) —
просто теперь не обязательно четырьмя секундами. Что не влезло в запрошенную длину, из плана
выбрасывается, кроме «включить» и первого куска.

**Ролик режет отсев, а не режиссёр, в трёх случаях**: поставщик нейросети не настроен (сегодняшнее
состояние, decision-10), никто из материала ещё не описан (ключ появился только что, часовая докатка
не дошла — заказывать порядок кадров, которых модель не видела, значит платить за случайный) и план,
в котором не оказалось ни одного нашего куска. Во всех трёх ролик собирается ровно так, как
собирался всегда, и заметить разницу неоткуда.

## Уборка оборванных загрузок

Тем же циклом, раз в час: строки в `pending_upload` старше суток — это телефон, который уже не
вернётся. Недособранный multipart в хранилище отменяется, ключ освобождается, строка снимается.
Отдельного процесса и крона нет — уборка едет вместе с очередью, и недоступное хранилище её
роняет, а не воркер.

## Тесты

Тесты живые: им нужны настоящий Postgres, настоящий бакет и `ffmpeg` с `ffprobe` — всё то же
локальное, что выше. Фикстуры фото, видео и звука рисует сам `ffmpeg`: бинарного, которое лежит в
репозитории не так, всего два вида — музыка в `tracks/` и три фотографии в `fixtures/`:
`exif-photo.jpg` и `exif-photo.heic` с EXIF (64×64, меньше килобайта каждая) и `portrait-photo.heic`
(кадр сенсора 96×64 с `irot`, снятый «стоя»: красный угол сверху слева, синий снизу справа, на глаз
64×96). Нарисовать их на месте нечем: EXIF `ffmpeg` не пишет, а HEIC не пишет вовсе; метаданные в
них проставлены руками — никакой камеры и ничего личного. Портретный HEIC собран кодировщиком
libheif (`heif-enc`) из JPEG с EXIF-поворотом 6, `pi-heif` кодировать не умеет. Повёрнутые кадры на
месте рисуются: фотографию с EXIF-поворотом — `pillow` (писать EXIF он умеет), видео — `ffmpeg` в два
прохода, потому что display matrix переживает только копирование: при перекодировке он разворачивает
саму картинку и матрицу убирает. Битый HEIC, на котором падает libheif, собран из `exif-photo.heic`
перебором байт (`CRASHING_HEIC` в `test_media.py`), а не лежит в репозитории.
**Каждый прогон чистит таблицы `jobs`, `ai_requests`, `media_speech` и `media_understandings`** в
базе из `DATABASE_URL`, так что не направляйте их на что-то ценное — в чекауте продукта отдельную
базу под тесты заводит `make test-montage`, при запуске отсюда руками база на вас. Проверки превью,
предложения отсева, понимания, речи и ролика пропускаются, если миграции API ещё не накатаны.
Исключения три. `test_selection.py`: отсев проверяется функциями над оценёнными кусками и кадрами,
нарисованными прямо в тесте, так что ни базы, ни `ffmpeg`, ни бакета ему не нужно. `test_rhythm.py`:
ритм проверяется на метрономе, нарисованном тут же с известным темпом, — нужен только `ffmpeg`.
`test_director.py` посередине: база ему нужна (описания, расшифровки и журнал запросов — это
строки), а `ffmpeg` и бакет нет — оценённый кусок там пишется руками, как в `test_selection.py`.

`test_journal.py` — живой целиком, и у него есть то, чего нет больше ни у кого: **второе
соединение**. Журнал читают, пока ролик собирается, поэтому он и проверяется так — посреди сборки
открывается отдельное соединение, то самое, которым журнал читает API, и смотрит, что записанное
уже видно, а прогресс склейки идёт по готовому куску, а не появляется разом в конце.

### Золотой снимок журнала

`test_journal_golden.py` собирает ролики по-настоящему (Postgres, бакет, `ffmpeg`, режиссёр —
записанным ответом, `fixtures/gemini_plan_journal.json`) и сравнивает всё, что воркер записал, со
снимками в `fixtures/`:

| Снимок | Сборка |
|---|---|
| `journal_director.json` | режиссировала нейросеть: мысль о плане, мысли о кадрах, части истории, рамка, «взял 1 из 2», «беру» по слову организатора, `left_out` со словами и без, `no_room`, `excluded`, отсев (`blur`, `exposure`, `unreadable`), разбор кадров |
| `journal_algorithm.json` | нейросети нет, режет отсев: «взял 1 из 3», `no_room`, `excluded`, `included`, отсев, разбор кадров; музыка полки (`track`, `bpm`, `cuts`) |

Снимок — мост между сервисами: его читают не Python-тесты, а тесты API и приложения, чтобы вести
настоящий вывод воркера через свой маршрут и свои экраны. Поэтому он самодостаточный JSON:

- `montage` — `status`, `duration_seconds` и `params` заказа, где `include_media_ids` и
  `exclude_media_ids` уже записаны метками файлов;
- `files` — файлы воспоминания в порядке съёмки (он же порядок метки: `f1`, `f2`, …): `label`, `kind`
  (`photo` / `video`), `position`, `captured_after_seconds` (секунд от первого кадра до съёмки
  этого — порядок галереи и границы серий), `duration_seconds` (у видео). По этому списку читатель
  заводит свои `media_items` и переписывает метки на настоящие id;
- `stages` — пять этапов в порядке пайплайна: `stage`, `state`, `started_at`, `finished_at`,
  `eta_seconds`, `done_count`, `total_count`, `outcome` (как в базе), `updated_at`;
- `entries` — все записи журнала в порядке записи, столбец в столбец: `n`, `stage`, `media` (метка
  файла или `null` — мысль про план в целом), `thought`, `decision`, `reason`, `series_size`,
  `story_part`, `story_part_title`, `source_from_seconds`, `source_to_seconds`, `labels`, `focus`
  (`{x, y, w, h}` или `null`), `created_at`. Метка `media` — та же, что `label` в `files`;
- `layout` — раскладка (`montage_frames`): `media`, `start_seconds`, `duration_seconds`, по порядку
  в ролике.

Что нормализовано, чтобы снимок был одним и тем же от прогона к прогону: uuid файлов → метки;
`bigserial` записей → `n` (1, 2, 3… по порядку записи); все метки времени (`started_at`,
`finished_at`, `updated_at`, `created_at`) — секундами от `2026-01-01T00:00:00Z` по месту во времени:
кто раньше кого — сохранено, сколько прошло — нет. Одна оговорка про порядок: записи этапа
«разбираем» (`understanding`) воркер читает из базы запросом без порядка, и снимок ставит их по
файлам в порядке съёмки — между собой они ничего не значат, а порядок строк в таблице у разных
прогонов разный.

Тест сравнивает снимок слово в слово, кроме измеренных длин (`layout`, `montage.duration_seconds`,
`assembly.outcome.seconds`): они допускают 0,2 с — кадр-другой кодировщика и сетки битов. Расхождение
падает с построчной разницей. Молча снимок не перезаписывается никогда — только явно:

```sh
MONTAGE_UPDATE_GOLDEN=1 python -m pytest test_journal_golden.py   # тесты в этот раз «пропущены»
git diff fixtures/journal_*.json                                  # посмотреть, что изменилось
```

Перезапись — нативно, не через `test-in-docker.sh`: рабочая копия там только на чтение. Снимок
читают API и приложение, поэтому изменившийся снимок — повод сказать им, а не только закоммитить.

Третий тест того же файла — ретрай той же задачи: первая попытка падает на склейке, в воспоминание
добавляют кадр, вторая проходит; после неё база совпадает с чистым заказом из того же материала.

В сеть не ходит ни один тест. Нейросеть (`test_ai.py`, а через неё и `test_speech.py`,
`test_understanding.py` и `test_director.py`) проверяется
на ответах, записанных руками по документации обоих API, — они лежат в `fixtures/`; транспорт
адаптера в тестах подменяется на тот, что отдаёт записанный файл и запоминает запрос, так что
проверяется и то, что ушло бы в сеть.
Поставщик сменил форму ответа — правится файл в `fixtures/`, а не тест.

## Как устроена очередь

Одна таблица `jobs` (`schema.sql`) на все типы задач:

| столбец | что в нём |
|---|---|
| `type` | какой обработчик звать |
| `ref` | id объекта, о котором задача |
| `status` | `queued` → `running` → `done` / `failed` |
| `attempts` | сколько попыток уже было |
| `run_after` | раньше этого момента задача не берётся |
| `last_error` | текст последней ошибки |

Цикл (`worker.py`): одним запросом берёт одну задачу со `status='queued' AND run_after <= now()`
через `FOR UPDATE SKIP LOCKED` и сразу метит `running` — второй воркер такую строку пропустит.
Успех → `done`. Исключение → `attempts + 1`, `last_error`, и либо `queued` с
`run_after = now() + 30с × 2^(попытка−1)`, либо `failed` после третьей попытки.

Пустая очередь → воркер ждёт, пока его разбудит сама база: триггер на `jobs` шлёт уведомление на
каждую вставку, поэтому задача — и из API, и из `enqueue` — подхватывается сразу, без паузы.
Уведомление, пропущенное за работой над другой задачей, ничего не подвешивает: ожидание всё равно
кончается через 30 секунд, и воркер смотрит в очередь сам.

Две вещи ломают побудку молча — очередь продолжает работать, но с задержкой до 30 секунд вместо
мгновенной. Первая: на базе, заведённой до появления триггера, его ставит тот же `worker.py init` —
его надо позвать один раз после обновления. Вторая: уведомления не проходят через пулер в режиме
транзакций (PgBouncer `transaction`, пулеры Supabase и Neon) — воркеру нужно прямое подключение к
Postgres, в отличие от API.

Без Redis и брокеров: один воркер, одна таблица. Это осознанный потолок — см. «Очередь задач» в
`architecture.md` корневого репозитория.
