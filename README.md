# montage

Фоновый обработчик Remember. Отдельный процесс на Python, наружу не смотрит: в цикле берёт задачи
из таблицы `jobs` в Postgres, выполняет и почти всё время спит. Единственный способ дать ему работу —
вставить строку в `jobs` (это делает API).

Сейчас он умеет шесть вещей: делать превью загруженного медиа (`media_preview`), считать по нему
предложение автоматического отсева (`media_screening`), разбирать, что на кадре и кто на нём
(`media_understanding`), расшифровывать речь в видео (`media_speech`), собирать ролик из материала
воспоминания (`montage`) и раз в час подчищать оборванные загрузки.

## Что нужно

- Python 3.11+
- Postgres 16
- `ffmpeg` и `ffprobe` в `PATH` — ими делаются превью
- Объектное хранилище: локально MinIO из `../api/docker-compose.yml`, в проде Cloudflare R2

## Postgres и хранилище

Канонная локальная база и бакет — те же, что у API, одной командой:

```sh
cd ../api && docker compose up -d
```

Если её ещё нет (или нужна отдельная), сгодится любой Postgres 16:

```sh
docker run --rm -d --name remember-pg \
  -e POSTGRES_USER=remember -e POSTGRES_PASSWORD=remember -e POSTGRES_DB=remember \
  -p 5432:5432 postgres:16
```

## Запуск

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env             # база и локальное хранилище
set -a && . ./.env && set +a     # внести в окружение: воркер читает только его

python worker.py init            # создать таблицы воркера
python worker.py run             # цикл разбора очереди, Ctrl-C для остановки
```

Своего чтения `.env` у воркера нет — переменные приходят из окружения, и на хостинге их задаёт
сам сервис. Имена хранилища — те же четыре, что читает API, так что вместо своего `.env` можно
внести его `../api/.env` целиком.

`init` можно звать сколько угодно раз: `schema.sql` идемпотентен (`CREATE TABLE IF NOT EXISTS`),
на чистой базе накатывается с нуля.

Необязательный `R2_REGION` (по умолчанию `auto`) — на случай хранилища, которому не всё равно,
чем подписан запрос.

`API_URL` и `INTERNAL_WORKER_TOKEN` нужны только готовому ролику — ими воркер стучится в API,
чтобы тот разослал пуш. Не заданы — сборка всё равно проходит, в логе остаётся предупреждение.

## Фиктивная задача

В другом терминале (с тем же окружением):

```sh
python worker.py enqueue dummy         # воркер её возьмёт и поставит done
python worker.py enqueue dummy fail    # ref=fail — упадёт и уйдёт в повтор
```

Второй вариант и есть проверка повторов: воркер отметит попытку, запишет ошибку и отложит задачу
(30 с, потом 60 с), а после третьей попытки поставит `failed`.

## Превью (`media_preview`)

Задачу ставит API, когда байты доехали в хранилище; в `ref` — id строки `media_items`. Воркер
качает оригинал и делает то, что показывает галерея:

| что загрузили | что получается | куда пишется |
|---|---|---|
| фото | миниатюра шириной 640 | `thumbnails/<id>.jpg` → `thumbnail_key` |
| фото | копия JPEG, длинная сторона до 2048 | `previews/<id>.jpg` → `preview_key` |
| видео | постер (кадр с первой секунды) | `thumbnails/<id>.jpg` → `thumbnail_key` |
| видео | копия 720p H.264 + AAC, faststart | `previews/<id>.mp4` → `preview_key` |

Дальше строка становится `ready`, а измеренная длина видео заменяет ту, что заявил телефон.
Оригинал не трогается. Меньше исходника ничего не увеличивается: маленькое фото так и остаётся
маленьким.

Фото, которое стало `ready` ещё до того, как воркер научился делать крупную копию, догоняется само:
`sweep_photos_without_previews` раз в час ищет `photo` + `ready` + пустой `preview_key` без уже
идущей задачи и ставит `media_preview` заново — на оригинале, который и так лежит в хранилище.
Повторной загрузки от участника не требуется. Задача, которая упала все три раза, следующим часом не
повторяется: её пробуют ещё раз через `CATCH_UP_AFTER_HOURS`, чтобы битый оригинал не молол очередь
круглые сутки, а час недоступного R2 не оставил старые фото без копии навсегда.

Упало — обычные повторы очереди, а после третьей попытки `media_items.status` тоже становится
`failed`, чтобы галерея перестала ждать и показала плейсхолдер.

`media_items` — таблица API (его миграция `004.do.media.sql`), montage только читает и пишет строки
по id. Схему заводят миграции API: `cd ../api && npm run migrate`.

## Предложение отсева (`media_screening`)

Задачу ставит сам воркер — в тот момент, когда строка становится `ready` (конец `media_preview`); в
`ref` тот же id `media_items`. Воркер качает оригинал и зовёт `selection.judge` — ту самую оценку,
которой потом решается, войдёт ли кадр в ролик, — и кладёт её ответ в две колонки, которые API
отдаёт галерее (его миграция `060.do.media-screening.sql`):

| столбец | что в нём |
|---|---|
| `screening_rejected` | `false` — анализ посмотрел и оставил, `true` — отбраковал, `null` — ещё не смотрел |
| `screening_reason` | почему отбраковал: `unreadable`, `blur`, `exposure`; у оставленного — `null` |

Это **предложение**, а не решение (doc-03, «Автоматический отсев брака как предложение»): организатор
видит его в галерее до заказа и правит списками «включить» / «исключить». На сам ролик колонки не
влияют никак — что войдёт, по-прежнему решает `selection.choose` в момент заказа, и пайплайн сборки
эти две колонки не читает вовсе.

`duplicate` сюда не попадает намеренно. Дубль — не свойство файла, а сравнение кадров между собой:
серия снимков в пределах двух секунд, из которой остаётся самый резкий (`selection._dedup` по всему
воспоминанию сразу). Сам по себе файл дублем не бывает, а вердикт, опирающийся на соседей,
переворачивался бы при каждой новой загрузке того же мгновения. Дедуп остаётся там, где он и был, —
в заказе.

Берётся оригинал, а не превью: ролик режется из оригинала, а 720p-перекодировка сглаживает ровно те
края, по которым меряется резкость, — предложение начало бы тихо расходиться с тем, что скажет сам
заказ о том же файле.

Медиа, ставшее `ready` до появления этой задачи, догоняется так же, как фото без крупной копии:
`sweep_media_without_screening` раз в час ищет `ready` + пустой `screening_rejected` без уже идущей
задачи и ставит `media_screening`. Файл, который не читается или в котором нет ни одного годного
кадра, получает `unreadable` и успокаивается — «не посчитано» навсегда не остаётся. Недоступное
хранилище — другое дело: это обычные повторы очереди, а после третьей попытки колонки так и остаются
`null` (сказать «брак» о файле, до которого не дотянулись, было бы неправдой) и задача повторяется
через `CATCH_UP_AFTER_HOURS`. Статус самой записи задача не трогает ни при каком исходе: кадр,
который анализ забраковал, остаётся в галерее и скачивается как любой другой.

## Ролик (`montage`)

Задачу ставит API, когда организатор заказал ролик; в `ref` — id строки `montages`, в её `params`
лежит заказ: `target_seconds`, `music_track_id`, `orientation`, необязательный `story_text` —
история ролика словами организатора (её читает только режиссёр, ниже) — и, необязательно, два
списка id медиа: `include_media_ids` и `exclude_media_ids` (ниже).

Ролик собирают четыре файла, и граница между ними жёсткая:

| файл | за что отвечает |
|---|---|
| `director.py` | **режиссёр**: план ролика от нейросети — порядок кусков, длина каждого, акцент |
| `selection.py` | **отсев**: что войдёт в ролик, в каком порядке и почему остальное не вошло |
| `assembly.py` | **сборка**: отобранные куски на общий холст и в один файл, `ffmpeg`-ом |
| `montage.py` | оркестратор: читает заказ, качает оригиналы, зовёт модули по очереди, пишет итог |

Первые два отвечают на один и тот же вопрос и отдают одно и то же: сначала спрашивают режиссёра, а
когда режиссёра нет (нет поставщика нейросети — сегодняшнее состояние), ролик режет отсев, как резал
всегда. В отсеве нет ни одной склейки, в сборке — ни слова про резкость, экспозицию и дубли: ей дают
готовый список кусков (длительность, откуда резать, место в ролике) и она их склеивает, не
спрашивая, почему именно эти. Любой из них заменяется, не трогая остальные, — этого и просит спека
(doc-03, «Сервис монтажа собран из отдельных модулей»); тем же швом пришиты понимание
(`understanding.py`, ниже) и режиссёр, и в него же дальше ляжет ритм.

Отсев отвечает на два вопроса по отдельности. `judge` смотрит один скачанный файл: читается ли он,
есть ли в нём годный кадр, где в нём лучший момент. `choose` из оценённых кусков выбирает те, из
которых выйдет ролик. Оба возвращают не только прошедшее, но и отклонённое — с причиной на каждом
куске: `unreadable`, `blur`, `exposure`, `duplicate`, `excluded`, `no_room`. Причины — короткие
коды, а не фразы для человека: их читает код, а показывает их потом приложение своими словами.

Пайплайн — «Montage-пайплайн» из `architecture.md` по шагам:

1. все `ready`-медиа воспоминания из базы; меньше трёх — не собираем (ниже);
2. оригиналы качаются во временную папку, она убирается сама;
3. план режиссёра (ниже), если есть кого спросить, — иначе отбор: кадры видео семплируются раз в
   секунду, размытые (дисперсия Лапласа) и
   пере-/недоэкспонированные (гистограмма) отсеиваются, серия снимков в пределах двух секунд по
   дате съёмки схлопывается в самый резкий кадр (нет даты — файл в дедупе не участвует). Что не
   влезло в `target_seconds` — отсекается по резкости. Порядок в собранном отбором ролике всегда
   хронологический, по дате съёмки, а без неё — по времени загрузки (в ролике по плану порядок
   назначает режиссёр). Файл, который не читается
   или в котором не нашлось ни одного годного кадра, просто не попадает в ролик; годных кусков
   осталось меньше трёх — не собираем. Выбор организатора («включить» и «исключить», ниже) этот
   шаг уважает поверх любой оценки;
4. каждый **отобранный** кусок нормализуется на общий для ролика холст, H.264, 30 fps, с паддингом
   по краям. Холст выбирает заказ: 1920×1080 (`landscape`, по умолчанию) или 1080×1920 (`portrait`);
   материал другой формы получает поля, а не обрезается — вертикальное видео на альбомном холсте
   получает поля по бокам, горизонтальное входит как есть. Отбор идёт раньше нормализации (в
   `architecture.md` шаги стоят наоборот) — чтобы не кодировать в 1080p то, что в ролик всё равно
   не войдёт;
5. сборка: клипы по 4 секунды вокруг лучшего момента, фото по 3 секунды (неподвижным кадром, без
   Ken Burns), кросс-фейд 0,5 секунды между кусками, сверху трек с fade in/out. Звука исходников
   в ролике нет — только музыка;
6. файл уезжает в `montages/<id>.mp4`, а обложкой — миниатюра шириной 640 в `montages/<id>.jpg`:
   кадр лучшего момента первого куска, а не нулевой кадр ролика. Кусок режется с центром на этом
   моменте, поэтому начинается он раньше — у клипа с телефона там сплошь и рядом чернота, а
   обложке черноты нельзя; строка становится `ready` с обоими ключами и длительностью, и воркер
   стучится в `POST {API_URL}/internal/montages/<id>/ready`, чтобы API разослал пуш. Кадр вырезать
   не удалось — ролик всё равно готов, `poster_key` остаётся пустым и API отдаёт `poster_url: null`,
   как у роликов, собранных до появления постеров;
7. временные файлы убираются вместе с папкой.

**Выбор организатора** — `include_media_ids` и `exclude_media_ids` в `params`, списки id из
`media_items`, оба необязательные. Отмеченное «исключить» не попадает в ролик никогда, каким бы
резким ни было. Отмеченное «включить» попадает всегда, если файл технически пригоден — читается и
в нём есть хоть один кадр, — даже когда алгоритм счёл кадры браком; не отменяет «включить» только
файл, в котором кадра нет вовсе, и это не мнение, а отсутствие картинки. Время под «включить»
тратится первым, и остальной отбор подстраивается под остаток `target_seconds`. Названное в обоих
списках сразу остаётся за бортом: заказать ролик заново можно, вынуть кадр из готового — нет.

**Треки** — три штуки: `warm`, `bright`, `calm`. Их рисует сам `ffmpeg` (`aevalsrc`, три синуса
аккордом под медленной волной) — в репозитории нет ни одного аудиофайла и ни одной чужой лицензии.
Это заглушка до настоящей подборки, а не выбор музыки.

**Оценка кадра** — пока только резкость. `architecture.md` просит ранжирование NIMA (ONNX, CPU);
модель, её происхождение и лицензия — открытый вопрос, и до ответа кадры сортируются по уже
посчитанной дисперсии Лапласа. Место помечено в коде (`selection.py`, `_best_moment`): меняется
одна функция, пайплайн вокруг остаётся.

Отказы без повторов: материала меньше трёх файлов, годного материала меньше трёх, весь материал
исключён организатором, неизвестный `music_track_id` и неизвестная `orientation`. Во всех пяти
воркер сам ставит `montages.status='failed'` с текстом причины и штатно завершает задачу — на
второй попытке ответ был бы тот же. Всё остальное (упал `ffmpeg`, недоступно хранилище) — обычные
повторы очереди, а после третьей попытки строка тоже становится `failed`, и у организатора
появляется «повторить».

`montages.error_text` API отдаёт всем участникам воспоминания, поэтому туда идёт короткая фраза для
человека, а не текст исключения: подробности (стек, вывод `ffmpeg`, адрес хранилища) остаются в
`jobs.last_error` и в логе, которые читает не пользователь, а тот, кто чинит.

`montages` — таблица API (его миграция `020.do.montages.sql`), montage только читает и пишет строки
по id.

## Облачная нейросеть (`ai.py`)

Три вопроса, которые воркер задаёт облачной модели: что происходит в кадре и кто на нём,
что сказано в видео, и в каком порядке из кусков складывается ролик. Задаются они через `ai.AI` —
других дверей к нейросети нет, и код, который спрашивает, не знает, кто отвечает:

```python
brain = ai.AI(conn)                                   # поставщика берёт из окружения
about = brain.describe_media([ai.Blob("image/jpeg", data)], cast=["человек-1"], ref=item_id)
```

Поставщик — переменной окружения, вместе с ключом и (необязательно) моделью:

| переменная | что в ней |
|---|---|
| `AI_PROVIDER` | `gemini` или `openai` |
| `GEMINI_API_KEY` / `OPENAI_API_KEY` | ключ выбранного поставщика |
| `GEMINI_MODEL` / `OPENAI_MODEL` | модель, если не устраивает та, что по умолчанию |
| `OPENAI_TRANSCRIBE_MODEL` | у OpenAI речь расшифровывает отдельная модель отдельной ручкой |

Не задано ничего (сегодняшнее состояние — ключа от человека ещё нет) — воркер **в сеть не идёт**:
каждый вызов пишет в лог, что он пропущен и никто ничего не отвечал, и возвращает `None`. Вызывающий
код на `None` откатывается к тому, что воркер умеет сам, — ролик собирается сегодняшним отбором.
Строка при старте (`cloud model: …`) говорит, есть модель или нет.

Различий между поставщиками два, и оба спрятаны внутри адаптеров: Gemini берёт видео целиком, а
OpenAI видео не принимает вовсе — клип ему описывают вырезанными кадрами (он об этом говорит
ошибкой); речь у Gemini — тот же запрос с аудио, у OpenAI — загрузка файла в свою ручку.

**Новый поставщик** — класс с `name`, `generate` и `transcribe` и одна строчка в `PROVIDERS`.
Ключ и модель он получит из `<ИМЯ>_API_KEY` и `<ИМЯ>_MODEL` сам.

### Журнал запросов

Каждый вызов через `ai.AI` ложится в таблицу `ai_requests` — строка заводится **до** обращения к
модели и закрывается ответом, так что упавший на полпути воркер всё равно оставляет запись о том,
что спрашивали. Наружу её никто не отдаёт, смотреть — руками:

```sh
psql "$DATABASE_URL" -c "select created_at, provider, operation, ref, status, took_ms,
  request->>'prompt', response from ai_requests order by id desc limit 20"
```

`status` — `sent` (спросили, ждём), `answered`, `failed` (в `error` — что пошло не так) и `skipped`
(поставщика нет, никого не спрашивали; `response` у такой строки пустой всегда). В `request` лежит
промпт и по строчке на каждый приложенный файл — тип и размер. Байтов медиа там нет намеренно:
оригиналы и так в хранилище, а копия материала в jsonb сделала бы эту таблицу самой большой в базе.
Ключа там нет тем более.

## Понимание кадров (`media_understanding`)

Задачу ставит сам воркер — концом `media_preview`, как только медиа стало `ready`; в `ref` — id
строки `media_items`. Облачная модель (через `ai.py`) отвечает одним-двумя предложениями, что
происходит в кадре, и списком действующих лиц — кто в нём есть. Ответ ложится в свою таблицу
`media_understandings` по id медиа и больше не пересчитывается: описанный кадр повторно в нейросеть
не уходит ни при втором ролике, ни при часовой докатке (doc-03, «Второй ролик из тех же медиа не
описывает заново уже описанные кадры»).

| столбец | что в нём |
|---|---|
| `media_id` | id строки `media_items`, одна строка на медиа |
| `memory_id` | чьего воспоминания метки ниже |
| `description` | что происходит в кадре |
| `cast_labels` | кто в кадре — метками этого воспоминания |

**Одни и те же люди и животные** узнаются самой моделью, своей системы распознавания у нас нет
(decision-9). Работает это так: перед каждым следующим кадром воспоминания из таблицы берутся все
метки, которые это воспоминание уже раздало («человек-1», «животное-1»), и уходят в запрос —
модель либо узнаёт кого-то из них, либо заводит следующего по счёту. Поэтому и задача на один
файл: состав растёт по кадру за раз. Метки стабильны внутри воспоминания и за его пределами не
значат ничего — «человек-1» в двух разных воспоминаниях это два разных человека.

**В модель уходит не оригинал**, а копии, которые сделал `media_preview`: фото — крупной копией,
видео — тремя кадрами из 720p-превью, вырезанными равномерно по клипу (края не берём: первый кадр
у телефонного видео сплошь и рядом чёрный). Кадрами, а не клипом целиком, хотя Gemini клип берёт:
OpenAI видео не принимает вовсе, а Gemini считает клип по его длине (258 токенов в секунду,
doc-11) — три кадра отвечают «что происходит и кто в кадре» у обоих поставщиков по цене трёх фото.
Движение при этом теряется, место помечено в коде (`understanding.py`).

Поставщик не настроен (сегодняшнее состояние) — **не описывается ничего**: задача завершается
штатно, в таблицу и в журнал не пишется ничего, кадр остаётся неописанным. Появится ключ —
`sweep_media_without_understanding` раз в час находит готовые медиа без описания и ставит задачу
сама, той же схемой, что и докатка фото без крупной копии: уже идущую не дублирует, а упавшую все
три раза пробует ещё раз через `CATCH_UP_AFTER_HOURS` — кадр, который модель не может прочитать,
иначе уходил бы к ней трижды в час, а это уже не процессор, а деньги.

## Речь в видео (`media_speech`)

Задачу ставит сам воркер — в конце `media_preview`, когда видео стало `ready`; в `ref` — id строки
`media_items`. Оригинал качается из хранилища, `ffmpeg` вынимает из него звук (моно, 16 кГц, AAC:
примерно это модель и слушает, а байтов в разы меньше), и расшифровка запрашивается через `ai.AI`.
Сказанное ложится в свою таблицу `media_speech`, одной строкой на медиа:

| столбец | что в нём |
|---|---|
| `media_id` | id строки `media_items` |
| `transcript` | слова, как они сказаны; пусто — речи в записи нет |
| `created_at` | когда расшифровали |

Кто говорит — не спрашиваем и не храним (decision-11): расшифровка ни к кому в кадре не
привязывается, и столбца под это в таблице нет.

Считается один раз: задача на уже расшифрованном видео ни в какую нейросеть не идёт и сразу
завершается — второй и следующие ролики из того же материала берут сохранённое (doc-03). Видео без
звуковой дорожки и видео, в котором никто не говорит, получают пустую расшифровку: это ответ, а не
пробел, и больше их никто не спрашивает.

Пока поставщик нейросети не настроен (сегодняшнее состояние — ключа нет), задача ничего не пишет и
штатно завершается: клип расшифруется, когда ключ появится. Сам себя он при этом не догонит —
видео, загруженные до ключа, ставятся в очередь руками:

```sh
python worker.py enqueue media_speech <id медиа>
```

## Режиссёр (`director.py`)

Своей задачи в очереди у него нет: он живёт внутри сборки ролика и спрашивается там, где раньше сразу
звали отсев. Нейросеть получает всё, что пайплайн уже знает о материале, и строит **план ролика**:

| что уходит в запрос | откуда |
|---|---|
| описание каждого кадра и кто в нём | `media_understandings` (`understanding.py`) |
| что сказано в клипе | `media_speech` (`speech.py`), первые 400 символов |
| сколько секунд этот файл вообще может дать | измеренная длина видео; фото — сколько попросят |
| история ролика словами организатора | `params.story_text` из заказа |
| запрошенная длина | `params.target_seconds` |
| пометка «этот кусок обязателен» | `params.include_media_ids` |

В ответ — порядок кусков, длина каждого и акцент: чем этот кусок важен. Порядок и длину берёт сборка,
акцент никуда не идёт и остаётся в журнале `ai_requests` вместе со всем ответом — там план виден
целиком. Расшифровки режутся по 400 символов намеренно: всё воспоминание едет в одном запросе, и
десять минут речи с одного клипа оплачивались бы словом.

**Выбор организатора режиссёр соблюдает так же, как отсев**, и это то же самое правило, записанное
во втором месте. «Исключить» в запрос не попадает вовсе — модель этого кадра просто не видит, и
назвать его не может; если всё-таки назовёт (чужой id, свой же id дважды) — такой шаг плана
выбрасывается. «Включить» уходит пометкой `must_include`, а если план его всё равно забыл — кусок
дописывается в конец плана. Не отменяет «включить» только файл, в котором нет ни одного кадра.

Длину каждого куска режиссёр назначает сам, в пределах от секунды до восьми: клип при этом никогда
не берётся длиннее, чем он есть, и режется по-прежнему вокруг лучшего момента (`selection.cut_to`) —
просто теперь не обязательно четырьмя секундами. Что не влезло в запрошенную длину, из плана
выбрасывается, кроме «включить» и первого куска.

**Ролик режет отсев, а не режиссёр, в трёх случаях**: поставщик нейросети не настроен (сегодняшнее
состояние, decision-10), никто из материала ещё не описан (ключ появился только что, часовая докатка
не дошла — заказывать порядок кадров, которых модель не видела, значит платить за случайный) и план,
в котором не оказалось ни одного нашего куска. Во всех трёх ролик собирается ровно так, как
собирался всегда, и заметить разницу неоткуда.

## Уборка оборванных загрузок

Тем же циклом, раз в час: строки в `pending_upload` старше суток — это телефон, который уже не
вернётся. Недособранный multipart в хранилище отменяется, ключ освобождается, строка снимается.
Отдельного процесса и крона нет — уборка едет вместе с очередью, и недоступное хранилище её
роняет, а не воркер.

## Тесты

Тесты живые: им нужны настоящий Postgres, настоящий бакет и `ffmpeg` с `ffprobe` — всё то же
локальное, что выше. Фикстуры фото и видео рисует сам `ffmpeg`, в репозитории не лежит ничего
бинарного. **Каждый прогон чистит таблицы `jobs`, `ai_requests`, `media_speech` и
`media_understandings`** в базе из `DATABASE_URL`, так что не направляйте их на что-то ценное — в
чекауте продукта отдельную базу под тесты заводит `make test-montage`, при запуске отсюда руками
база на вас. Проверки превью, предложения отсева, понимания, речи и ролика пропускаются, если
миграции API ещё не накатаны.
Исключение — `test_selection.py`: отсев проверяется функциями над оценёнными кусками и кадрами,
нарисованными прямо в тесте, так что ни базы, ни `ffmpeg`, ни бакета ему не нужно. `test_director.py`
посередине: база ему нужна (описания, расшифровки и журнал — это строки), а `ffmpeg` и бакет нет —
оценённый кусок там пишется руками, как в `test_selection.py`.

В сеть не ходит ни один тест. Нейросеть (`test_ai.py`, а через неё и `test_speech.py`,
`test_understanding.py` и `test_director.py`) проверяется
на ответах, записанных руками по документации обоих API, — они лежат в `fixtures/`; транспорт
адаптера в тестах подменяется на тот, что отдаёт записанный файл и запоминает запрос, так что
проверяется и то, что ушло бы в сеть.
Поставщик сменил форму ответа — правится файл в `fixtures/`, а не тест.

### В контейнере — когда ffmpeg на машине сломан или его нет

```sh
cd ../api && docker compose up -d --wait   # Postgres на 5432 и MinIO на 9000
cd -
./test-in-docker.sh                        # аргументы уходят в pytest: ./test-in-docker.sh -k preview
```

Свой `ffmpeg` едет внутри образа (`Dockerfile`), так что версия и состояние системного не значат
ничего. База и хранилище — те же, уже поднятые на хосте, и база тут всегда стенда: `DATABASE_URL`
скрипт прописывает сам, перенаправить его нечем, так что `jobs` этот прогон чистит у стенда.
Контейнер ходит в них через
`host.docker.internal`, порты публикует `docker-compose.yml` api. Переменные окружения скрипт задаёт
сам, значениями из `.env.example`, — своего `.env` для этого прогона не нужно. Рабочая копия
подключается томом и только на чтение, поэтому образ пересобирается лишь при смене
`requirements.txt`.

## Как устроена очередь

Одна таблица `jobs` (`schema.sql`) на все типы задач:

| столбец | что в нём |
|---|---|
| `type` | какой обработчик звать |
| `ref` | id объекта, о котором задача |
| `status` | `queued` → `running` → `done` / `failed` |
| `attempts` | сколько попыток уже было |
| `run_after` | раньше этого момента задача не берётся |
| `last_error` | текст последней ошибки |

Цикл (`worker.py`): одним запросом берёт одну задачу со `status='queued' AND run_after <= now()`
через `FOR UPDATE SKIP LOCKED` и сразу метит `running` — второй воркер такую строку пропустит.
Успех → `done`. Исключение → `attempts + 1`, `last_error`, и либо `queued` с
`run_after = now() + 30с × 2^(попытка−1)`, либо `failed` после третьей попытки.

Пустая очередь → воркер ждёт, пока его разбудит сама база: триггер на `jobs` шлёт уведомление на
каждую вставку, поэтому задача — и из API, и из `enqueue` — подхватывается сразу, без паузы.
Уведомление, пропущенное за работой над другой задачей, ничего не подвешивает: ожидание всё равно
кончается через 30 секунд, и воркер смотрит в очередь сам.

Две вещи ломают побудку молча — очередь продолжает работать, но с задержкой до 30 секунд вместо
мгновенной. Первая: на базе, заведённой до появления триггера, его ставит тот же `worker.py init` —
его надо позвать один раз после обновления. Вторая: уведомления не проходят через пулер в режиме
транзакций (PgBouncer `transaction`, пулеры Supabase и Neon) — воркеру нужно прямое подключение к
Postgres, в отличие от API.

Без Redis и брокеров: один воркер, одна таблица. Это осознанный потолок — см. «Очередь задач» в
`architecture.md` корневого репозитория.
